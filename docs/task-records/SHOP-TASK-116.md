- 入口 `process_stripe_checkouts(db, gateway, now, limit) -> int`：`now` 带时区抛 ValueError（先于访问数据库）。每轮先做会话处理、再做付款方式类型补齐，两种扫描各自最多 `limit` 条，都按上次查询时间从早到晚、从没查过的排最前（MySQL 不支持 NULLS FIRST，按 `last_polled_at IS NOT NULL` 排）、同时刻按 ID；逐条先以只改这一列的 UPDATE 写上次查询时间并提交，再处理。返回两种扫描选中并处理过的记录数之和（Stripe 不可用而跳过的、选中后重读时已变为 expired 或订单已不是待支付的也算）。另导出 `has_pending_checkouts(db, now)`（只读）供定时任务判断未配置时是否跳过。
- 会话处理只选待支付订单的、不是 expired 的记录中的 creating、Stripe 到期时间已过的 open 与 complete。逐条以普通读取得记录与订单的支付到期时间、结束读事务后处理；调用 Stripe 时不持有任何数据库锁，之后由 SHOP-TASK-112、113、114 的函数按「会员 → 订单 → Stripe 会话记录」加锁并重查。取消一律经 `cancel_after_stripe_end`，操作者为 system；它返回 changed 时这条留到下一轮。
  - creating：不论是否已过 Stripe 到期时间都调用 `reconcile_creating_checkout`（到期前以同一幂等键与同一快照重试，到期后对账）。记为 expired 且订单已过本地支付到期时间时不给记录 ID 调用 `cancel_after_stripe_end`；未过期的订单不动（之后由访客再发起或现有的超时取消处理）。取得 open 或 complete 时重读记录，按会话的实际状态接着处理。结果不明（pending）订单保留不动，不凭时间取消；`under_review` 已由 SHOP-TASK-112 写告警时间并记 `stripe_checkout_needs_review`。
  - open（已过 Stripe 到期时间）：查询会话。expired 且核对属于这条记录（会话 ID、元数据的创建幂等键相同、livemode 为假）才给记录 ID（`seen_status` 为 open）调用 `cancel_after_stripe_end`，记录的 expired 与订单的取消在它的同一事务里完成，不看本地支付到期时间；complete 或已付款时以这次查询到的对象调用 `confirm_checkout`；仍为 open、状态不认识、核对不符与查询不成都按 Stripe 不可用。
  - complete：查询会话。已付款时以查询到的对象调用 `confirm_checkout`；未付款、会话仍为 complete 且核对属于这条记录、PaymentIntent 为 `canceled` 或 `requires_payment_method`（Stripe 给出的付款失败）时给记录 ID（`seen_status` 为 complete）调用 `cancel_after_stripe_end`，记录记为 expired、订单取消；`processing`、`requires_action` 等其余状态、查询不到 PaymentIntent 时继续等待。
  - 确认的结果：paid 不再处理；refunded（SHOP-TASK-117 写成退款尝试、记录已为 expired）在订单已过本地支付到期时间时不给记录 ID 调用 `cancel_after_stripe_end`；needs_review 已由 SHOP-TASK-117 写告警时间；unavailable（如会话为 open 而已付款，取不到可核对的对象）按 Stripe 不可用；pending 对 complete 记录按仍无结果，对 open 记录（会话 complete 而付款未定，记录已改为 complete）留给之后各轮按 complete 处理。
- 告警（运营告警邮件接入前先记 error 级日志，只含类别与记录 ID）：creating 记录自创建满 24 小时（与 SHOP-TASK-112 转人工的起点相同，实际由它先记 `stripe_checkout_needs_review`）、open 记录自 Stripe 到期时间满 24 小时仍无法确定时写告警时间并记 `stripe_unreachable`；complete 记录自完成时间满 24 小时仍无结果（含查询不可用）记 `stripe_payment_needs_review`。订单不取消、库存继续预留。告警时间以带条件的 UPDATE（告警时间仍为空、状态未变）写入并提交后才记日志，每条记录至多一次；告警时间已非空的记录（含 SHOP-TASK-112 与 SHOP-TASK-117 写的）不再记任何告警，告警时间也不清空，但仍照常查询，Stripe 恢复后按会话的实际状态处理。
- 付款方式类型补齐：单独扫描付款状态为 paid、付款方式类型为空且有会话 ID 的记录，不论订单与记录状态（确认之后订单已是 demo_paid；迟到付款的 expired 记录也在内），同样按上次查询时间轮转，逐条调用 `fill_payment_method_type`。补齐只是补字段，不计入「有待处理的记录」；不论结果都不再处理、不记告警、不写告警时间，留到下一轮。
- 定时任务：`app/jobs.py` 的 `stripe_checkouts_job`（名称 `stripe_checkouts`，own_transactions，逐条提交）排在超时取消之后、每日库存重置之前，两种扫描每轮各最多 `STRIPE_CHECKOUT_BATCH_LIMIT`（等于 `CANCEL_BATCH_LIMIT`）条、合计至多两倍。每次按 `get_settings()` 的当前配置建 `StripeHttpGateway`（配置被清空后即为未配置，调用一律归为 unavailable、不发请求）。Stripe 未配置时，没有待处理的记录（会话处理要选的记录）才不建适配器、返回 0（跳过算成功）；有待处理的记录则照常处理、按不可用计时与告警。手动补跑命令 `python -m app.jobs process-stripe`（`process_stripe`，写法照 `cancel-expired`：未配置数据库退出码 2、任务失败 1、成功 0，日志只含任务名、处理条数与异常类名）。模块说明与用法随之补充。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 上次查询时间在处理之前、以只改这一列的独立事务写入并提交，不与处理在同一事务：被调用的对账、确认与取消函数各自提交与回滚。先写使处理中途抛异常的记录也轮到队尾，不会每轮卡在队首。
  - creating 记录「自创建满 24 小时写告警时间并记 `stripe_unreachable`」的分支只在对账函数没写告警时间时兜底：`reconcile_creating_checkout` 对创建满 24 小时的记录先于调用 Stripe 就转人工并记 `stripe_checkout_needs_review`，所以实际记的是后者，每条仍只告警一次。
  - creating 经对账取得 open 时，若已过 Stripe 到期时间，按 open 再查询一次会话（对账的回放之后已查过一次），与「对账取得会话时按会话实际状态继续处理」一致，多一次 Stripe 调用。
  - 会话 expired 或付款失败时，取消前核对会话 ID、元数据里的创建幂等键与记录相同、livemode 为假，不符按 Stripe 不可用（验收没有写这一核对）；查询结果为 live 或 rejected 也按不可用。
  - Stripe 到期时间已过而会话仍为 open（时钟误差）算「仍无法确定」，自 Stripe 到期满 24 小时记 `stripe_unreachable`。
  - 确认返回 refunded 时（验收未写这一情形）只在订单已过本地支付到期时间才取消，与「creating 对账记为 expired 后」同一规则；未过期时订单没有活动记录，访客可再发起，到期后由现有的超时取消处理（HANDOFF 0.53：订单随后可再发起支付或按现有规则取消）。
  - complete 记录的会话未付款时不调用确认（记录已是 complete，确认只会原样返回 pending），付款失败的判定直接用同一次查询到的 PaymentIntent 状态；open 记录查询到 complete 而未付款的会话时调用确认，由它把记录改为 complete，`confirm_checkout` 因会话缺 `latest_charge` 会再查询一次。
  - 补齐扫描另要求会话 ID 非空：没有会话 ID 时补齐函数返回 skipped、不调用 Stripe，选中它只会占用上限。
  - 「有待处理的记录」含已告警的记录（如已转人工的 creating）：未配置时任务照常执行，它们不调用 Stripe，只写上次查询时间。
  - `stripe_checkouts_job` 另有参数 `gateway_factory`（默认 `StripeHttpGateway.from_settings`），供测试换成替身；运行器与命令都用默认值。
- 留给之后的任务：webhook 的 `checkout.session.async_payment_failed` 后按现有规则取消（规划块「已阻塞」的 webhook 接口；在那之前付款失败只由本任务的定时查询发现）；运营者处置转人工的会话记录（规划块「已阻塞」，涉及支付状态，登记前须按设计闸门写明核实条件并经 Kelvin 批准）；运营告警邮件（规划块「后续计划」，把本任务的 `stripe_unreachable`、`stripe_payment_needs_review` 日志改为发邮件）；Stripe 退款尝试的定时重试与复查（规划块「已阻塞」的 Stripe 退款规则）。
