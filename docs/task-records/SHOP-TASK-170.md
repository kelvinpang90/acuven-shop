# SHOP-TASK-170 后台运费与演示汇率的读取与保存规则

- [x] 按 `docs/DESIGN.md` 1.16（提交 `e9a1c93`）「计价、优惠、积分与库存」第 9 条（管理员在后台 A06 一次保存整页的运费与演示汇率：范围、取值、两步核对、行 ID 不复用、审计、生效与版本号的含义）与 `docs/HANDOFF.md` 0.67 的落实写法，新增服务层 `app/services/admin_shipping_rates.py`，读取整页数据、保存整页修改，供 SHOP-TASK-171 的后台接口调用。改动只在 `app/models/shipping.py`、`app/services/admin_shipping_rates.py`、`tests/test_admin_shipping_rates.py` 与本文件。不做接口与前端；未改迁移、`app/services/shipping.py`、现有测试、`.platform/`、CI、部署配置；未装依赖；未改设计。设计闸门：DESIGN 1.16（提交 `e9a1c93`）与 HANDOFF 0.67，运费与演示汇率的后台维护。
- 读取：`load_admin_rates(db) -> AdminRates`，只发两条只查列值的 SELECT（运费表、汇率表），不写库、不写审计。`AdminRates` 为 `states`（16 个州属，按区域代码即 MY-01 到 MY-16）、`other`（兜底行；库里缺这一行时为 None）、`countries`（按国家代码）、`fx_rates`（按国家代码）；排序在 Python 里做，不随 MySQL 排序规则变化。运费行为 `ShippingRateRow(id, zone_code, fee_sen, version)`，汇率行为 `FxRateRow(id, country_code, currency_code, currency_decimals, rate, version)`，`rate` 为 `canonical_rate` 给出的规范形式（`format(value, "f")` 后去掉小数部分尾随的零，全为零时连小数点一起去掉；34.000000 为 34、0.310000 为 0.31、100 为 100）。
- 保存：`save_admin_rates(db, admin_account_id, states, other, countries, fx_rates, now) -> AdminRates`，参数写法照 `save_site_settings`（`now` 为不带时区的 UTC 时间，交给 `record_audit`；函数开头先回滚此前的事务，`admin_account_id` 须在调用前取出）。四组的元素为：州属与兜底 `KeepFee(id, version, fee_sen)`；国家运费 `KeepFee`、`RemoveRow(id, version)` 或 `AddCountryFee(country_code, fee_sen)`；汇率 `KeepFxRate(id, version, rate)`、`RemoveRow` 或 `AddFxRate(country_code, currency_code, currency_decimals, rate)`。每组须为 list 或 tuple。
- 两种异常：`RatesInvalid`（第一步，接口回 `rates_invalid`）与 `RatesChanged`（第二步，接口回 `rates_changed`），都只带英文说明、不回显提交的值。
- 第一步，不碰数据库：每组的元素类型合乎上面的写法（州属与兜底只能是 `KeepFee`）；行 ID 与版本号为整数；运费为 0 到 999,999 的整数，`type(value) is int`，布尔值不算；汇率须为 `str`，整串匹配 `[0-9]{1,6}(?:\.[0-9]{1,6})?`（`fullmatch`，尾随换行也不通过），且 `Decimal` 值大于 0；新增的国家为 `[A-Z]{2}`、在 `phone_regions()` 里且不是 MY；币种为 `[A-Z]{3}` 且不是 MYR；小数位为 0 到 3 的整数（布尔值不算）；同一组里行 ID 不重复，国家运费与汇率各自的新增行之间国家不重复。任一不通过即抛 `RatesInvalid`，此前不发任何 SQL（含回滚）。
- 第二步，锁行核对：回滚后先执行 `lock_shipping_rates_statement()`、再执行 `lock_fx_rates_statement()`（各为 `SELECT … FOR UPDATE`、按 id 排序、无条件、带 `populate_existing`，照 `lock_site_setting_statement`）。按行 ID 核对：州属、兜底、国家、汇率四组各自列出的行 ID 集合须恰等于该组现有的行（第一步已保证组内不重复，集合相等即一一对应），版本号与锁住的当前值相同；新增的国家在该组的现有行里没有（同一请求里列为删除的除外）。任一不通过即回滚、抛 `RatesChanged`、不写入。
- 写入：运费表的行按 id 顺序处理——列为删除的删除并写 `admin_shipping_rate_removed`；运费与当前值不同的写新值、版本号加一并写 `admin_shipping_rate_changed`；汇率表同理（`admin_fx_rate_removed`、`admin_fx_rate_changed`），汇率按 `Decimal` 数值比较（0.31 与 0.310000 相同）、写入 `Decimal(提交的字符串)`。随后 `db.flush()` 把删除写进库，再按请求顺序插入新增的国家运费、新增的汇率（版本号 1），各写 `admin_shipping_rate_added`、`admin_fx_rate_added`。删后再增同一国家写两条审计。最后在同一事务里用 `load_admin_rates` 读出整页：有任何一行改动则提交，整页都未变时回滚（不写审计）；两种情况都返回读出的整页数据。写入途中出现任何异常都回滚后再抛出。
- 审计：经 `record_audit` 写入，对象类别 `shipping_rate` 或 `demo_fx_rate`，对象 ID 为该行 ID（删除的行取删除前的 ID，新增的行取 flush 后的 ID）。旧值与新值为「区域代码 运费仙数 v版本号」（如 `SG 2000 v1` → `SG 2500 v2`）或「国家代码 币种代码 小数位 规范汇率 v版本号」（如 `JP JPY 0 34 v1` → `JP JPY 0 35.5 v2`）；新增的行旧值为空、新值带 v1，删除的行新值为空、旧值带删除前的版本号。
- 行 ID 不复用的落实（HANDOFF 0.67（1））：`app/models/shipping.py` 的 `ShippingRate` 与 `DemoFxRate` 表参数由 `MYSQL_TABLE_OPTIONS` 改为 `{**MYSQL_TABLE_OPTIONS, "sqlite_autoincrement": True}`（模块内常量 `_TABLE_OPTIONS`），模块说明写明原因：SQLite 不声明自增时主键沿用 rowid 的默认行为，会把删掉的最大 ID 再分配给新行；MySQL 由迁移 0004 建表时的 AUTO_INCREMENT 保证，8.0 起自增计数持久化。这一项只改 SQLite 的建表语句，列、约束与 MySQL 的建表语句不变，迁移未改。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 兜底组按「组」处理，与其他三组同为序列，核对时须恰是兜底行这一行；读取结果里的 `other` 是单行（库里缺该行时为 None，此时保存的兜底组须为空才通过核对）。
  - 第一步把「元素类型不对、行 ID 或版本号不是整数」算作结构不合格（`RatesInvalid`）；行 ID 或版本号是整数但对不上，归第二步（`RatesChanged`）。接口层（SHOP-TASK-171）如先以请求体模型校验结构，这里的类型检查是第二道。
  - 汇率只接受 `str`，`Decimal` 或浮点数一律 `RatesInvalid`（第 9 条「以十进制字符串提交、不经浮点数」）。整数部分带前导零的写法（如 `00.31`）在 1–6 位数字之内，按设计照收，存入后读取与审计都是规范形式。
  - 保存后的整页数据在提交前、于同一事务里读出，返回的正是本次提交的内容；未变时也在回滚前读出。
  - 审计顺序：运费表的改动与删除（按行 id）→ 汇率表的改动与删除（按行 id）→ 新增的国家运费 → 新增的汇率（按请求顺序）。设计未规定顺序，测试按此断言。
- 留给之后的任务：读写接口（请求体 64 KB 上限、422 `rates_invalid`、409 `rates_changed`）由 SHOP-TASK-171 接上；A06 页面待视觉稿补齐、经 Kelvin 审阅后另行登记。
- 验证到什么程度：人工逐条对照验收标准、DESIGN 1.16 第 9 条与 HANDOFF 0.67 原句自查。新增 `tests/test_admin_shipping_rates.py`（SQLite 内存库按模型建表，写入与迁移 0005 相同的演示数据）：读取的顺序、行 ID 与版本号、规范汇率，`canonical_rate` 的各种写法，读取只发 SELECT；第一步每类不合格（运费 -1、1,000,000、布尔值、浮点数、字符串；汇率 0、0.000000、七位整数、七位小数、正负号、指数、前后与中间空白、尾随换行、以小数点开头或结尾、空串、全角与阿拉伯-印度数字、千分位逗号、NaN、浮点数与 Decimal 对象；新增国家小写、MY、不在列表里、三位、全角；币种 MYR、小写、两位；小数位 4、-1、布尔值；组内行 ID 重复；新增行国家重复；州属或兜底列为删除、州属组里有新增、汇率组里放运费新增）都抛 `RatesInvalid`、不发任何 SQL、数据与审计不变，同一请求里另一行合格的修改也不写入，以及取值范围两端可保存的对照；第二步四组各自版本号不符、漏列现有的行、列了不存在的行、州属行 ID 放进国家组、新增已有的国家或汇率都抛 `RatesChanged` 且数据与审计不变；删后再增同一国家（运费与汇率）成功、新行 ID 不同且版本号为 1、各写两条审计；删掉 ID 最大的一行并提交后新增的行 ID 仍大于它（运费与汇率）；拿删除前读到的行 ID 与版本号再保存被拒（只删、删后再增两种）；改了值的行版本加一、未改的行不变、审计的旧值与新值与操作者、时间正确，同一行再改版本到 3；新增与删除的审计；整页未变只发 SELECT、不写审计、返回与读取相同；现有 0.310000 提交 0.31、0.310000、00.31、000000.310000 都视为未变；提交 7.700 读取与审计都是 7.7；两条锁定查询按 MySQL 方言编译带 FOR UPDATE、按 id 排序、带 populate_existing，保存时先锁运费表后锁汇率表且是头两条语句；两张表的 SQLite 建表语句带 AUTOINCREMENT，MySQL 建表语句照旧是 AUTO_INCREMENT；删除国家运费后 `quote_shipping` 对该国返回兜底运费、删除汇率后 `reference_amount` 返回 None、改了州属运费后计价取新值与新版本号。每条测试的文档字符串写明它守住的 DESIGN 1.16 第 9 条或 HANDOFF 0.67 原句，或验收里的约定。测试交由 PR 的必需 CI 检查 backend 执行（Worker 沙箱不跑后端测试）；`tests/test_shipping.py` 与 `tests/test_demo_shipping_seed.py` 未改，模型的改动只影响它们在 SQLite 上的建表语句。SQLite 不支持行锁，锁定在 MySQL 上的效果只按代码与 MySQL 方言编译的语句审阅；生产 MySQL 8.0 上「删除最大 ID、重启后不复用」在 CI 与沙箱里测不到，只按 MySQL 8.0 自增计数持久化的行为与迁移 0004 的建表语句（`id` 为单列整数主键，SQLAlchemy 生成 AUTO_INCREMENT）审阅。检查命令结果由 Worker 另行记录。
