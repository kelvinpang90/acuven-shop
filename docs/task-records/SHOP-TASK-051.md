- 接口与字段：两个接口都经 SHOP-TASK-036 的 `require_admin`（无有效后台会话 401 `admin_session_required`），路由器用 SHOP-TASK-027 的 `_NoStoreRoute`，处理函数与依赖产生的全部响应（含错误）都带 `Cache-Control: no-store`（路径存在但方法不匹配的 405 由框架回答，不在此列）；不写日志。
  - `GET /api/admin/store-design?lang=en|zh|ms`（默认 en，不合法 422 沿用 `app/api/pay.py` 的 `_language`，不回显所给的值）：返回 `theme`、`accent`（为空时 `null`）、`home_blocks`（按位置排序的 `{block, visible}`）、`featured`（按位置排序，每项 `product_id`、`slug`、`name`、`published`；已不满足 `published()` 的也列出、`published` 为 `false`）、`choices`（全部满足 `published()` 的商品，每项 `product_id`、`slug`、`name`，按商品 ID 升序）与由 cookie 算出的 `csrf_token`。名称按语言取，缺少时回退英文。设置行不存在时主题与主色取默认值、区块缺行时按默认顺序补齐（与 SHOP-TASK-045 相同），不补写库。不写审计。
  - `PUT /api/admin/store-design`：检查顺序 413（请求体逐块读，超过 8 KB，先于一切）→ 415（不是 JSON）→ 401 → 403（`require_admin_csrf`，`X-CSRF-Token` 缺、错或不止一个时 `csrf_failed`）→ 422（结构）→ 业务校验。请求体只有 `theme`（字符串）、`accent`（字符串或 `null`）、`home_blocks`（恰好 4 项 `{block, visible}`，`block` 恰为 hero、how、categories、featured 的一个排列，数组顺序即位置）与 `featured_product_ids`（0 到 4 个不重复的正整数，上限 2147483647，数组顺序即位置），四个字段都必填，严格类型，多出字段或结构不合格 422，`detail` 为经 `_body_errors` 的错误数组（只有位置、类型与固定消息，不回显输入值）。成功（含与当前完全相同）200，返回保存后的 `theme`、`accent`、`home_blocks`、`featured`（字段同 GET，不含 `choices` 与 `csrf_token`）。
- 校验与错误码（业务校验 422，错误体 `{"detail": "<错误码>"}`，依次判断）：主题不在 `THEMES` 为 `theme_invalid`（大小写不同也算不在）；主色非 `null` 且不在该主题的 `THEME_ACCENTS`（含属于别的主题的主色、空串）为 `accent_invalid`；任一精选商品不存在或此刻不满足 `published()`（直接复用 `app/services/catalog.py` 的判定）为 `featured_unavailable`。任一校验不通过时回滚，不写入任何东西。主题与主色的校验不查库，在锁定之前；精选商品的校验在锁定之后。
- 锁定与事务（`save_store_design`）：先回滚本请求此前的事务（此前只有 `require_admin` 的读取；管理员 ID 在此之前取出），再以 `lock_setting_statement()`（`SELECT … FOR UPDATE`，带 `populate_existing`）锁定单例行，使锁定成为新事务的第一条语句——MySQL 默认的 REPEATABLE READ 下，锁定之后才读取的当前设置能看到等锁期间别人提交的保存。单例行不存在时在保存点（`begin_nested`）里按默认值插入，撞上单例槽唯一约束（`IntegrityError`）即回滚该保存点，然后再锁定。锁定后校验精选商品、读取当前设置（主题、主色、区块表的原始各行、精选各行的商品 ID）；与请求完全相同时回滚（释放锁，连同可能刚插入的默认行），返回当前设置，不写审计。否则改写主题、主色与更新时间，先删除原有区块与精选各行并 flush，再按请求插入（避免位置、区块与商品的唯一约束在重排时冲突），写审计，一起提交。提交后公开接口 `GET /api/store-design` 的下一次请求即读到新设置。
- 审计：用 SHOP-TASK-035 的 `record_audit` 写一条 `admin_store_design_saved`，对象类别 `store_design`、对象 ID 为设置单例行的 ID；`old_value` 与 `new_value` 为无空格的 JSON 数组 `[主题, 主色或 null, 区块串, [精选商品内部 ID…]]`，区块串按位置依次为区块代号 H、W、C、F 加 1 或 0（如 `H1W1C1F0`）；旧值的区块按读取规则补齐为四个，精选含已下架的商品。不含商品名称或 slug。序列化后超过 255 个字符即抛 `AssertionError`（不截断；按现有主题、主色与 INT 上限的商品 ID，最长约 90 个字符）。
- 偏离与取舍，请审阅（未改需求与设计）：
  - 待确认的设计问题（未停下，按任务合同实现）：A08 写「之后下架的商品仍留在列表中」，而合同要求保存时任一精选商品此刻不满足 `published()` 即 `featured_unavailable`。两者合起来，精选里有下架商品时，管理员只改主题或区块也保存不了，必须先把下架的商品移出。这不是自相矛盾（GET 照常列出它、`published` 为 `false`，页面可以提示移出），但可能不是预期的操作体验；若希望保存时放行「原已在精选里、之后才下架」的商品，需要改合同与 A08 说明。同理，与当前完全相同的请求只要含下架商品也是 422 而不是 200（业务校验在相同判断之前）。
  - `PUT` 也接受可选的 `lang`（en、zh、ms，默认 en），只决定返回的商品名称；不合法时与请求体错误一起在 403 之后回答 422。合同只写了 GET 的 `lang`，PUT 的返回「字段同 GET」需要一个语言。
  - 精选商品的 `name` 在请求语言与英文都缺少时为 `null`（只会是不满足 `published()` 的商品，`published()` 要求英文名称齐全）；`choices` 的 `name` 总是字符串。
  - 「与请求完全相同」按区块表的原始各行比较，不按补齐后的结果：区块表缺行（正常不会发生）时视为不同并整体重写，借此补齐四行。
  - 精选商品的可见性只在保存时判断，不锁商品行：保存提交前并发下架的商品仍可能写入精选，前台按 `published()` 不显示它（与之后下架的商品相同）。
  - 审计操作名与对象类别常量放在 `app/services/store_design.py`（`ADMIN_STORE_DESIGN_SAVED`、`AUDIT_TARGET_STORE_DESIGN`），与 `app/services/admin_orders.py` 的做法相同；`app/services/admin_auth.py` 不在本任务允许改动的路径内。
