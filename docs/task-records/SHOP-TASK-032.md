- 营业日期与时刻：`business_date(now)` = (UTC 时间 + 固定 8 小时) 的日期，不依赖时区数据库（马来西亚不实行夏令时）；UTC 15:59:59 仍是当天，UTC 16:00:00（马来西亚 0 点）起是下一天。运行器每分钟一轮，所以马来西亚 0 点后的第一轮即执行当天的重置。只重置当前营业日期，不补过去的日期：运行器停了一整天时那一天不再重置。
- 有效预留口径：每个规格所有 `awaiting_demo_payment` 订单（含已过支付到期时间但尚未取消的）的订单行件数之和；已支付及之后的状态、已取消的订单不算；规格已删除（`variant_id` 为空）的订单行不计。当日可用 = max(初始库存 − 有效预留, 0)。重置覆盖全部规格（含停用的），只改 `available_stock`，不改 `daily_initial_stock`，不改订单、退款与积分记录（重置里的超时取消除外，它本来就会取消已到期订单）。
- 步骤与加锁顺序（`reset_daily_stock(db, now)`）：
  1. 读该日期的记录并结束这次只读事务。已 `succeeded`：不做任何改动，返回已完成。
  2. 另开一个事务认领，按第 1 步看到的记录决定：没有记录时插入 `succeeded`（完成时间 = 当前时间、SKU 数 0、尝试次数 1）；有 `failed` 记录时用带条件的 UPDATE（`result = 'failed'` 才命中）改为 `succeeded`、写完成时间、清空异常类名、尝试次数加一。插入撞上唯一约束或 UPDATE 未命中即回滚、返回已完成。
  3. 在同一事务里执行 SHOP-TASK-021 的 `expire_overdue_orders`（不限张数）：让它在绑同一连接、以保存点加入本事务的会话里执行（与 SHOP-TASK-031 的 `run_job` 相同的做法），它的逐张提交只释放保存点。
  4. 一条 `SELECT … ORDER BY id FOR UPDATE` 按 SKU 规格 ID 从小到大锁住全部规格（与 SHOP-TASK-020 扣库存、SHOP-TASK-021 加回库存的顺序一致，避免死锁），再统计有效预留，写当日可用与明细，把 SKU 数更新为实际值后提交。
  5. 任一步出错（含认领时的锁等待超时或锁错误）：回滚，再在独立事务里记录失败——先用带条件的 UPDATE（`result = 'failed'` 才命中）把尝试次数加一、记下异常类名；未命中则插入 `failed` 记录（尝试次数 1、无完成时间），插入撞上唯一约束（已有记录，含 `succeeded`）即放弃；所以永远不把 `succeeded` 改回 `failed`。记录失败本身出错时回滚并放弃。然后把原异常交给调用方。
- 只生效一次的保证：认领记录与重置在同一事务里，提交前对其他执行者不可见。MySQL 上同一日期并发执行时，首次执行的后到者阻塞在同一唯一键上（插入），从 `failed` 记录重试的后到者阻塞在同一记录的行锁上（条件 UPDATE）；前者提交后，后到者插入冲突或 UPDATE 未命中，回滚并返回已完成，不写第二份明细、不再改写库存；前者回滚时后到者继续认领。另一个执行者的失败记录也走带条件的写入，不覆盖 `succeeded`。
- 运行器与补跑命令（`app/jobs.py`）：`default_jobs()` 为超时取消、每日库存重置（`reset_daily_stock`）两项。重置任务先查当前营业日期是否已有 `succeeded` 记录，有则不调用、返回 0（跳过算成功）；否则调用重置，失败按运行器规则只记日志、下一轮重试，连续失败满 10 分钟按 SHOP-TASK-031 停写心跳、容器不健康。人工补跑：`docker compose exec shop_jobs python -m app.jobs reset-stock`（`shop_jobs` 不在时可用 `docker compose run --rm --no-deps shop_jobs python -m app.jobs reset-stock`），执行一次当前营业日期的重置后退出：完成或当日此前已完成 0；失败 1；未配置 `SHOP_DATABASE_URL` 2。
- 日志：成功时 `stock reset <营业日期> succeeded: <SKU 数> skus`，失败时 `stock reset <营业日期> failed: <异常类名>`，另有运行器原有的 `job reset_daily_stock done: <n> changed` / `failed: <异常类名>`；不记订单号、个人资料、连接串或异常消息原文。重置服务本身不写日志。

  - 认领事务在 MySQL 上用 READ COMMITTED（`_begin`）：默认的 REPEATABLE READ 在超时取消的第一次查询时取快照，之后统计有效预留的普通查询仍读那个快照，会漏掉锁规格等待期间已提交的下单，把当日可用算多。READ COMMITTED 下统计在锁住全部规格之后读最新已提交的数据：已扣过库存的下单都已提交、都被计入；尚未扣库存的下单排在规格锁之后，从重置后的值上扣。SQLite 不支持该级别，测试里不设。

  - 失败时有两条日志（重置任务带营业日期的一条与运行器原有的一条）。
  - `tests/test_jobs.py` 的调整只为新增的任务：检查超时取消加回库存件数的五个用例改为只运行默认列表里的超时取消任务（`_cancel_only()`），断言不变；默认任务名列表加上 `reset_daily_stock`；会话工厂不可用的用例每轮多一次开会话与一条 `job reset_daily_stock failed: OperationalError`；原来以 `reset-stock` 代表未知子命令的断言改用 `reset-everything`（`reset-stock` 现在是合法子命令，其退出码在 `tests/test_stock_reset.py` 里测）。没有删减或放宽原有用例。
