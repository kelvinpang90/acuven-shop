# SHOP-TASK-087 积分的退款返还与追回规则

- [x] 按 `docs/DESIGN.md` 1.11（提交 `2d13250`）「计价、优惠、积分与库存」第 4、5 条（退款批准时按原逐件快照返还未过期的抵扣积分并追回获得积分；余额不足时扣至 0，缺口记待抵扣；累计返还 ≤ 实际抵扣、累计追回 ≤ 实际获得）与「订单与退款状态」（以后获得积分先偿还待抵扣，不出现负余额），以及 `docs/HANDOFF.md` 0.46 记录的 Kelvin 2026-10-10 决定 1（返还以整单为单位，按该单在各批次的净抵扣从后到期的批次起返还，已过期的批次不返还），在 SHOP-TASK-086 之上实现退款时的积分规则与预估：`app/services/points_refund.py`；测试见 `tests/test_points_refund.py`。不接入退款审核与申请接口；未改 `app/services/points.py`、模型、迁移与设计，未加表。
- 入口：`apply_refund_points(db, order_id, refund_request_id, points_back, points_reversed, now)`（退款批准时调用）与 `estimate_refund_points(db, order_id, points_back, points_reversed, now)`（退款申请页在提交前调用，不需要退款申请 ID），都返回 `RefundPoints(returned, reversed_from_balance, debt_added)`：实际返还、从余额追回与记入待抵扣；`reversed_total` 为后两者之和。页面的 `refund.points_back` 取 `returned`，`refund.points_reversed` 取 `reversed_total`。两个积分数由调用方按被退的件的逐件快照 `points_discount` 与 `points_earned` 合计得出，本模块不读逐件快照。入参校验沿用 SHOP-TASK-086：积分不是 int（含 bool）抛 `TypeError`、负数抛 `ValueError`，ID 不是正整数抛 `ValueError`，当前时间不是 datetime 抛 `TypeError`、带时区抛 `ValueError`；流水时间为截到整秒的当前时间。
- 返还顺序与已过期份额：该单在每个批次的净抵扣为该单在该批次的 `redeem`、`release` 与 `refund_return` 之和取负（与 `release_points` 同一口径）。按批次到期时刻降序、同时刻按批次 ID 降序（抵扣顺序的相反）依次分配应返还的积分，每个批次分到的不超过其净抵扣；分到已过期批次（当前时间截到整秒后晚于到期时刻）的部分不返还、不记流水，但照样占去应返还的积分；分到未过期批次的部分写 `refund_return`。全部净抵扣分完仍有剩余的部分不返还，所以累计返还不超过实际抵扣。
- 追回顺序与待抵扣（在返还之后，批次剩余已计入本次返还）：先从该单获得的批次（未过期时）的剩余扣，再从该会员其他未过期批次按到期时刻升序、同时刻按批次 ID 升序扣，都写 `refund_reversal`（订单记被退款的订单）；仍不足的缺口写一条批次为空的 `debt_add`，所以不出现负余额；之后获得积分由 SHOP-TASK-086 的 `earn_points` 先偿还待抵扣。已过期批次的剩余不扣（之后由到期处理记为到期）。
- 累计上限：该单获得的积分（该单的批次的 `points`，没有批次为 0）减去该单以往各次退款的 `refund_reversal` 与 `debt_add` 之和小于应追回的积分时抛 `ValueError`、不写记录（记入待抵扣的缺口也算已追回）；返还超出时不抛错，只还到净抵扣为止。
- 锁与重复调用：先以普通读取订单的 `member_id`，再以 SELECT … FOR UPDATE 锁会员行（`populate_existing`），锁后加锁读重新读取订单的 `member_id`、会员状态、该会员的全部批次（`populate_existing`）与流水，累计上限也以此为准。调用方（退款审核）已持有订单行锁，这里的加锁顺序是订单 → 会员，与 SHOP-TASK-086 的会员 → 订单相反；与注销并发时 MySQL 可能判定死锁并回滚其中一方，由调用方按现有的数据库错误处理回答，不另做重试。同一退款申请已有积分流水时不再写，返回由这些流水求得的结果（不看这次给的积分数）。只 flush、不提交，不写日志。
- member_id 为空的处理：订单的 `member_id` 为空（游客订单或会员已注销）时不写记录、返回全零；锁后发现订单已不属于该会员或会员已不是 active（与注销并发）时同样不写记录、返回全零。预估在订单的 `member_id` 为空或会员不是 active 时也返回全零。
- 预估：只读、不写库、不锁行，用普通读取同样的数据、按同一规则在当前状态（已批准退款之后，不计审核中的申请）上算出三个数；应追回超出累计上限时同样抛 `ValueError`。预估与批准时可能因到期或余额变化而不同，以批准时为准。
- 偏离：未改设计，未发现须停下的设计问题。说明几处取舍，请审阅：
  - 契约把「被认领的游客订单」列为 `member_id` 为空的情形，但认领（`app/services/member_sms_login.py`）会把订单的 `member_id` 设为认领的会员。这样的订单没有抵扣与获得积分（认领不追发积分），函数照常走规则：返还与追回都是 0、不写记录、返回全零，结果与契约一致；调用方若给出非零的应追回积分会因累计上限抛 `ValueError`。
  - 退款申请须属于该订单，否则抛 `ValueError`（契约未写，防止流水挂到别的订单的申请上）；这一核对在 `member_id` 为空的判断之前。
  - 不核对退款申请的状态，也不核对两个积分数与逐件快照是否一致，由接入退款审核的任务保证。
  - 重复调用的判断在会员与订单的核对之后：会员已不是 active 时即使该申请已有流水也返回全零。
  - 已过期批次的份额不记流水，所以它的净抵扣不减少；之后的部分退款仍先分给未过期批次，未过期批次分完才落到已过期批次，累计返还仍不超过实际抵扣。
- 留给之后的任务：接入退款审核（批准时在同一事务里调用 `apply_refund_points`，审核结果显示返还与追回的积分）与退款申请页的积分预估（`estimate_refund_points`，显示 `refund.points_back` 与 `refund.points_reversed`），按 HANDOFF 2026-10-11 与 2026-10-12 决定所列的会员结账与会员订单任务登记；后台 A03 的积分一行随之加回。
- 验证到什么程度：人工逐条对照验收标准、DESIGN 1.11 原句与 HANDOFF 0.46 的 Kelvin 决定自查，并核对写入的流水符合 SHOP-TASK-084 的检查约束（`refund_return` 为正、`refund_reversal` 为负且批次非空、`debt_add` 为正且批次为空，三者都带退款申请）。`tests/test_points_refund.py` 用 SQLite 内存库（每个连接打开外键检查，并断言已打开）按模型建表，经 SHOP-TASK-086 的函数准备批次与流水，覆盖：DESIGN 第 4 条算例只退第一件 A（返还 120 记在原抵扣的批次、追回 8 从本单批次扣）；抵扣跨两个批次时后到期的先还、同到期时刻按批次 ID 降序还；两个批次都未过期、先到期批次已过期而后到期批次未过期、两个都已过期三种情形下已过期批次的份额不返还也不记流水；算例三件逐次退时累计返还到 300 为止、累计追回到 19 后再追回抛错且不写记录；已记待抵扣计入追回上限；追回先本单批次、再其他批次按到期升序（不按 ID）、已过期批次不扣、本单批次已过期时整笔记待抵扣；余额不足时扣至 0 并记待抵扣、之后获得积分先偿还；游客订单、注销后 `member_id` 已清空的订单与锁后读到会员已注销时不写记录；退款申请属于别的订单时抛错；同一退款申请重复调用（含记入待抵扣的情形）不重复；预估不需要退款申请 ID、不写库、没有变化时与批准结果一致（含已过期份额与待抵扣的情形）、在已批准退款之后的状态上计算、游客订单为全零、超出上限抛错；积分与当前时间的入参校验。每条测试写明它守住的设计或 Kelvin 决定的哪一句。锁后发现订单已不属于该会员与并发时的死锁依赖 MySQL 行锁，SQLite 测试不能复现，未在真 MySQL 上做并发验证。这些测试与已有后端测试只由 PR 的必需 CI 检查 backend 执行，Worker 沙箱不跑 pytest。检查命令结果由 Worker 另行记录。
