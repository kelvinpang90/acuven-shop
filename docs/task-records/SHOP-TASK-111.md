- 适配器 `StripeHttpGateway(settings, transport)`（协议 `StripeGateway`，写法照 `sms_provider.py`）：可注入的传输函数 `Transport`（`HttpRequest(method, url, params, headers) -> HttpResponse(status, body, headers)`，非 2xx 也作为响应返回，连不上或超时抛消息固定的 `TransportError`）；默认的 `urllib_transport` 只用标准库：只发 GET 与 POST（GET 把参数按顺序放进查询串，POST 为表单编码的请求体），带 `Accept: application/json`，超时 5 秒（套接字超时），不重试，不跟随重定向，地址不是 `https://` 时不发请求，响应体最多读 64 KiB 加 1 字节，响应头名转为小写。认证头为 `Authorization: Bearer <密钥>`；不发送 `Stripe-Version` 头，沿用账户默认的 API 版本（2026-10-15 的核验即按账户默认版本完成，升级账户 API 版本前须先在测试环境重跑核验，模块文档字符串写明）。未配置时六个调用都归为 `unavailable`、不调用传输函数。六个调用：
  - `create_checkout_session(form, idempotency_key)`：`POST /v1/checkout/sessions`，表单按调用方给出的 `(名, 值)` 序列原样发送，带 `Idempotency-Key`。
  - `retrieve_checkout_session(session_id)`：`GET /v1/checkout/sessions/{id}`，参数只有 `expand[]=payment_intent.latest_charge`。
  - `expire_checkout_session(session_id)`：`POST /v1/checkout/sessions/{id}/expire`，无表单、无幂等键。
  - `create_refund(form, idempotency_key)`：`POST /v1/refunds`，表单原样发送，带 `Idempotency-Key`。
  - `retrieve_refund(refund_id)`：`GET /v1/refunds/{id}`。
  - `list_refunds(payment_intent_id, starting_after=None)`：`GET /v1/refunds`，参数依次为 `payment_intent`、`limit=100`，给了 `starting_after` 时再加它；一次一页，翻页由调用方按 `has_more` 与最后一笔的 ID 继续。
  - 适配器不自行添加任何表单参数，也不传 `payment_method_types`（核验显示 Checkout 已不接受它，付款方式由 Stripe 后台设置决定）。对象 ID 按路径段编码；对象 ID、`starting_after` 或幂等键为空串时抛 `ValueError`（编程错误，消息固定，不发请求）。
- 归类（`StripeResult(outcome, value, replayed, error)`，`outcome` 为 `StripeOutcome` 的 ok / live / rejected / unavailable）：
  - 2xx 且响应是 JSON 对象、对象合格时为 `ok`，`replayed` 为响应头 `Idempotent-Replayed` 是否为 `true`（头名不分大小写），`value` 是按白名单取出的对账字段：会话 `CheckoutSession`（`id`、`status`、`payment_status`、`livemode`、`currency`、`amount_total`、`client_reference_id`、元数据里的 `order_id` 与 `create_key`、`url`、`expires_at`，以及 `payment_intent` 的 `PaymentIntentInfo`：`id`、`status`、`livemode` 与 `latest_charge.payment_method_details.type`）；退款 `Refund`（`id`、`status`、`amount`、`payment_intent`（ID；展开为对象时取其 `id`）、元数据里的 `attempt_id`）；列表 `RefundPage`（这些退款与 `has_more`）。`customer_details`、`customer_email`、账单资料、姓名、邮箱与卡号片段一律不取，原始对象不出适配器。会话要求 `object` 为 `checkout.session`、退款为 `refund`、列表为 `list` 且 `data` 为数组，`id` 须为非空字符串，否则归 `unavailable`；列表里任一退款不合格整页归 `unavailable`。白名单里其他字段缺失或类型不对时取 `None`（整数字段不接受布尔值）；`payment_intent` 未展开（只是 ID 字符串）时只有 ID，`latest_charge` 未展开时付款方式类型为空。
  - 三个会话调用的 `ok` 结果里，会话或其 PaymentIntent 的 `livemode` 为 `true` 时改归 `live`（带会话字段与回放标记；不是 rejected：会话可能已经建成），并记一条 error 级日志，内容只有类别 `stripe_livemode`。
  - 409 与 429 以外的 4xx、且响应体是带 `error` 对象的 JSON 时归 `rejected`，`error` 为 `StripeError(http_status, type, param, code)`，不带 `message` 原文；是否说明没有建成对象由调用方按状态码与错误内容一起判断（第 8 条：不单凭状态码）。
  - 409、429、3xx、5xx、其他状态码、传输函数抛 `TransportError` 或 `OSError`（超时、连接失败）、响应体超过 64 KiB、2xx 而不是 JSON 对象，以及 4xx 而响应体不是带 `error` 对象的 JSON，都归 `unavailable`。
  - 除 `stripe_key_not_test`、`stripe_livemode` 两类外不写日志。适配器 repr 只显示是否已配置，`HttpRequest` 的地址、参数与请求头和 `HttpResponse` 的响应体与响应头都不进 repr，异常消息固定；返回值只有上面的类别与白名单字段，不含密钥、邮箱或请求、响应原文。
- 签名校验 `verify_webhook_signature(payload, signature_header, secret, now) -> bool`：从头里取 `t` 与全部 `v1`，以签名密钥对「`t` 的十进制、一个英文句点、请求体」做 HMAC-SHA256，十六进制结果与任一 `v1` 以 `hmac.compare_digest` 比较相等（逐个比较全部 `v1`）、且 `now`（不带时区的 UTC；带时区时按其时区换算）与 `t` 相差不超过 300 秒（过去与将来都算）才通过。头缺失或不是字符串、签名密钥为空、任一项不是 `名=值`（含空项）、`t` 不是 1–20 位十进制数字或出现两次、没有 `v1`、签名不符或超出容差都返回 `False`；不抛异常、不写日志。`v0` 等其他项忽略。
- 测试替身与依赖：`FakeStripeGateway(*results)` 在内存里记下每次调用的 `FakeStripeCall(method, path, form, idempotency_key)`（GET 的查询参数记在 `form`；路径与参数和真实适配器共用同一拼法，表单与幂等键不进 repr），结果按调用顺序从 `results` 依次取出，取完后返回 `unavailable`；替身原样返回编排的结果，不做 livemode 归类。`get_stripe_gateway(request)` 是 FastAPI 依赖：`app.state.stripe_gateway` 已设置时用它（测试以此注入替身），否则按 `request.app.state.settings` 构造真实适配器（未配置也返回实例，调用时归为 `unavailable`），写法照 `get_sms_provider`。
- 告警先记日志：设计里写「告警」的两处（非测试密钥、livemode 为真）先各记一条 error 级日志，只含类别；适配器没有本站记录 ID，带记录 ID 的告警由调用方另记。由运营告警邮件任务（规划块「后续计划」）改为发邮件。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 传输类型没有沿用 `sms_provider.py` 的 `HttpRequest` / `HttpResponse`：那里只有 POST、表单是映射且没有响应头，本任务要 GET、按顺序的参数序列与 `Idempotent-Replayed` 响应头，所以在本模块另定义同名的两个类型与 `TransportError`（消息为 `stripe request failed`），写法相同。
  - 「响应过大」的判定：默认传输多读 1 字节，适配器见到超过 64 KiB 的响应体即归 `unavailable`（不靠截断后 JSON 解析失败），注入的传输函数返回的大响应同样如此。
  - 配置判定里两个地址除以 `https://` 开头外另要求其后非空（只写 `https://` 视为未配置）；未检查地址是否只到主机。
  - `rejected` 不带回放标记（验收只要求 ok 带）；`live` 带回放标记与会话字段，供调用方记下会话后另记带记录 ID 的告警。
  - 非测试密钥的日志在 `stripe_configured` 里记，所以构造适配器与之后站点设置接口的判定都会触发；同一进程只记第一次，之后换成另一个非测试密钥也不再记。
  - 对象 ID 或幂等键为空串时抛 `ValueError`，与未配置的判定无关（编程错误先于归类）。
  - 签名校验对头的格式取严格写法：出现空项、不含 `=` 的项或重复的 `t` 都不通过；`t` 限 1–20 位数字（不接受正负号、小数与空白内的数字）。
