# SHOP-TASK-132 支付页 P06 与结果页 P07 的 Stripe 请求模块

- [x] 按 `docs/DESIGN.md` 1.12（提交 `acf576e`）「Stripe 测试环境支付」第 2、3、4、5、9 条、`docs/UX.md` 0.11 的 P06、P07 与 `docs/HANDOFF.md` 0.54、0.55 的落实写法，在 `frontend/src/api/pay.ts` 接上支付页视图的三个 Stripe 字段、游客 Stripe 发起与确认接口、现有支付与取消接口的 409 `method_changed` 与 503 `stripe_unavailable`，并提供 P06 交给 P07 的「取消时会话已付款」内存交接。设计闸门：DESIGN 1.12（提交 `acf576e`）与 HANDOFF 0.55，支付状态的请求与归类（金额与状态的判定都在服务端）。不改页面与路由，不改后端，不改设计，不装依赖。
- 三个字段（`PayOrder`，含义照 `app/services/payment.py` 的 `PayOrder` 注释写进类型注释）：`payment_route`（待支付时为 `"stripe"` 或 `"simulated"`，其他状态为 `null`）、`stripe_state`（不是 expired 的 Stripe 记录的状态 `"creating"`、`"open"`、`"complete"`，creating 且已告警为 `"under_review"`，没有为 `null`）、`stripe_refunded`（本单有来源为会话的 Stripe 退款尝试）。`readPayOrder` 的读取与校验写法不变，与现有字段一样不另做字段校验。
- 两个接口：
  - `startStripe(language, orderNumber, csrfToken, signal?)` → `POST /api/pay/stripe/start?lang=<语言>`（`stripeStartUrl`，查询参数只有 lang）；`confirmStripe(orderNumber, csrfToken, signal?)` → `POST /api/pay/stripe/confirm`（`STRIPE_CONFIRM_URL`，不带查询参数）。两者同源 cookie、`cache: "no-store"`、Accept 与 Content-Type 为 `application/json`、`X-CSRF-Token` 为调用方给出的令牌，JSON 请求体只有 `order_number`；中止信号交给 fetch，中止与网络中断一样归 `network`。
  - 发送部分抽成模块内的 `postJson`（同源、no-store、JSON 请求头、可选中止信号，网络中断与中止返回 `null`），`postWrite` 与两个新函数共用；`postWrite` 不传中止信号，行为不变。
  - `startStripe` 的归类（`StripeStart`）：`redirect`（200 且 `result` 为 `redirect`、`checkout_url` 是字符串且 `new URL` 解析后 protocol 为 `https:`，带地址 `url`）、`complete`（200 且 `result` 为 `complete`、`checkout_url` 为 `null`）、`closed`（409 `order_not_payable`）、`method_changed`（409 `method_changed`）、`under_review`（409 `stripe_under_review`）、`unavailable`（503 `stripe_unavailable`）、`expired`（401）、`csrf`（403）、`failed`（其他状态、其他 detail、响应体不是 JSON 或不是对象、200 而地址缺少、不是字符串、解析不了或不是 https）、`network`。
  - `confirmStripe` 的归类（`StripeConfirm`）：`paid`、`confirming`、`not_paid`、`refunded`（200 且 `result` 为这四个值之一，列表为 `STRIPE_CONFIRM_RESULTS`）、`expired`（401）、`csrf`（403）、`failed`（其他，含 200 而 `result` 为其他值）、`network`。
- 现有写接口的两种新回答：`WriteReply` 加 `method_changed`（409 `method_changed`，支付与取消都适用）与 `unavailable`（503 `stripe_unavailable`）；其他 409 与 503 的归类不变（`CLOSED_DETAILS` 照旧为 closed，其余为 failed）。`settle` 把它们分别变成 `{ kind: "method_changed" }` 与 `{ kind: "unavailable" }` 两种新 `WriteOutcome`；`runPayment` 与 `runCancel` 的签名不变。
- 交接：`rememberPaidNotCancelled(orderNumber)` 把订单号记在模块内的变量里（不进地址、history 的 state、localStorage、sessionStorage 或 cookie）；`takePaidNotCancelled(orderNumber)` 只在记下的订单号与给出的相同时返回 `true`，不论是否相同都清除记录（读一次即失效，重新打开或刷新页面后模块重新加载，不再显示）。P06 在 SHOP-TASK-135 调用 remember，P07 在 SHOP-TASK-133 调用 take。
- 测试（`frontend/src/api/pay.test.ts`，vitest，fetch 以替身代替，不加测试依赖）：两个新接口的地址、方法、查询参数、请求头（恰为 Accept、Content-Type 与 X-CSRF-Token）、请求体（只有 `order_number`）与中止信号；发起与确认的每种归类各一例，含 409 与 503 的其他 detail、200 而地址为 http、`javascript:`、相对地址、解析不了、`null`、数字或缺少时归 failed；网络中断与中止归 network（中止用的替身照验收标准写成参数带类型的 `vi.fn((input, init) => …)`，从 `mock.calls` 取地址时不用 `String(…)`，而是与 `stubFetch` 共用的 `requestUrl` 按 string、URL、Request 分别取出地址字符串——对 `RequestInfo | URL` 直接调用 `String` 会触发带类型规则 `@typescript-eslint/no-base-to-string`，这样同样不让 any 流出）；支付与取消遇到 409 `method_changed` 与 503 `stripe_unavailable` 时的回答与 settle 的结果，以及其他 409、503 仍为 failed / error；交接读一次即失效、订单号不同时返回 false 且同样清除；交接与两个接口不写 localStorage、sessionStorage、cookie 或 history。每条测试的注释写明它守住的 DESIGN、UX、HANDOFF 或验收标准原句。现有测试的断言未改，夹具 `payOrder` 补上三个新字段（`payment_route` 为 `"simulated"`、`stripe_state` 为 `null`、`stripe_refunded` 为 `false`）。
- `frontend/src/pages/PayPage.test.tsx` 与 `frontend/src/pages/PayResultPage.test.tsx` 只在各自 `payOrder` 夹具默认值里补上这三个字段，其余一字未改。
- 偏离与按验收标准未写死之处的取法（未改设计，未发现须停下的设计问题）：
  - `frontend/src/pages/PayPage.tsx` 未改：它的 `settle` 对两种新结果落到 switch 之后的 `setFailed(true)`，显示现有的 `common.error_retry`，与此前归 failed 时相同；唯一的差别是支付时不执行 `kind: "error"` 分支里的 `setRetry(null)`（此前 409 `method_changed` 与 503 都不会出现在待重试的支付之后，影响只到 SHOP-TASK-134、135 接上为止）。
  - 200 的响应体为 JSON 但不是对象（如 `null`）时按「不合格」归 failed。
  - 发起接口的 201 等其他 2xx 按「其他状态」归 failed；确认接口同样只认 200。
