# SHOP-TASK-070 发送短信验证码接口

- [x] 按 `docs/DESIGN.md` 1.11（提交 `2d13250`）「权限与资料保护」第 1 条（白名单号码先过人机挑战再发短信验证码，号码按所选或输入的国家码规范化为 E.164）、第 3 条（注册、短信登录与结账验证是同一个短信验证流程，不暴露账号是否存在）与「失败、并发与重试」（开关关闭时在人机挑战之前即拒绝；托管人机挑战、限流、Redis 或 MySQL 不可用时停发；覆盖不足时展示明确错误），以及 `docs/HANDOFF.md` 0.41（短信验证与个人资料，Kelvin 2026-10-08 决定），新建 `app/api/sms.py` 提供公开的 `POST /api/sms/send`（`app/main.py` 挂上路由），调用 SHOP-TASK-069 的 `send_verification`；测试见 `tests/test_sms_api.py`。核验不单独开接口。未改服务层、模型与设计，未加表或迁移，未改 `.platform/`、CI、部署配置与前端，未装依赖。设计闸门：DESIGN 1.11（提交 `2d13250`）与 HANDOFF 0.41。
- 接口：路由器用 SHOP-TASK-027 的 `_NoStoreRoute`，处理函数与依赖产生的全部响应（含 413、415、422、`get_session` 的 503 与各结果的错误）都带 `Cache-Control: no-store`；路径存在但方法不匹配的 405 由框架在路由之外回答，不在此列（不含请求内容）。不需要会话与 CSRF，不读会员会话与订单访问 cookie。不写日志。
- 处理顺序（沿用 `app/api/orders.py` 的写法）：请求体逐块读，超过 4 KB（`MAX_BODY_BYTES`）即 413 `request body too large`，先于一切，不看 Content-Length 是否如实；读完之后不是 JSON（媒体类型不是 `application/json`，不分大小写、可带参数）即 415 `request body must be JSON`；再校验结构，422 照 `app/api/pay.py` 的 `_body_errors`，每条错误只给位置、类型与固定消息；结构通过后以 `app/services/phone.py` 的 `normalize_phone(phone, phone_region)` 规范化（与游客下单相同，以加号开头时以输入为准），不成立（含地区代码不合法）为 422，一条 `{"type":"phone_invalid","loc":["body","phone"],"msg":"invalid phone number"}`。之后才取会话、Redis 客户端与两个适配器。
- 字段（都必填、严格类型，多出字段 422）：`phone`（字符串）、`phone_region`（字符串）、`purpose`（`checkout`、`register`、`login`、`reset_password` 之一，区分大小写；`delete_account` 与其他值都是 422 `literal_error`，注销确认在会员注销任务里接上）、`captcha_token`（1 到 2048 个字符的字符串，上限取 `app/services/captcha.py` 的 `MAX_TOKEN_LENGTH`）。
- 结果与状态码：`sent` 200 `{"status":"sent"}`；`sms_disabled` 403、`not_whitelisted` 422、`captcha_failed` 403、`rate_limited` 429、`undeliverable` 422 `sms_undeliverable`、`suspended` 503 `sms_suspended`，错误体为 `{"detail":"<错误码>"}`。提交由发送函数负责。发送函数抛 `SmsVerificationError`（处理中 MySQL 出错或服务商调用抛异常）时回滚会话（回滚本身出错也吞掉，会话随后由 `get_session` 关闭），回答 503 `sms_suspended`。数据库未配置时照 `get_session` 的 503 `database is not configured`，不另转换。登录与重设用途对未注册号码照常发送，本接口不查会员表，响应与已注册号码相同。
- 依赖：服务商与人机挑战适配器经 SHOP-TASK-067 的 `get_sms_provider`、`get_captcha_verifier` 注入；Redis 客户端由本文件的 `get_sms_redis_client` 取得——调用 `app/services/rate_limit.py` 的 `get_redis_client`，抛 `RateLimitUnavailable`（未配置或连接串不对）时返回 `None`，不经 `_NoStoreRoute` 变成 503 `service_unavailable`；`None` 交给发送函数，由它在开关、白名单与人机挑战之后按停发处理。未用 `get_optional_redis_client`。来源取 `client_source(request)`，时间取不带时区的 UTC。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 发送函数在结算或释放时可能抛 SHOP-TASK-068 的 `SmsBudgetError`（每日预算记录不成立，SHOP-TASK-069 记录段写明原样抛出），验收只写了 MySQL 出错。本接口把它与 `SmsVerificationError` 一样处理：回滚会话、503 `sms_suspended`，不让它成为不带 no-store 的 500。此时短信可能已由服务商发出，但没有 `sent` 记录，之后的核验会是 `no_pending`。
  - 4 KB 上限是本接口自己的常量，没有复用 `app/api/pay.py` 的 `_json_body`（它固定为 8 KB）；读取与判断的写法与它相同。
  - `not_whitelisted` 与 `sms_undeliverable` 的 422 错误体是字符串 `detail`，与结构错误的 422（`detail` 为列表）可按类型区分。
  - 不按用途另做限流或区分：四种用途共用发送函数里的同一白名单、人机挑战、限流和每日预算（DESIGN 1.11「失败、并发与重试」）。
- 留给之后的任务：核验在登录、注册与密码重设任务里各自调用 SHOP-TASK-069 的 `verify_code` 接上；注销确认用途在会员注销任务里接上；前端（结账第 1 步、注册、登录与重设页的发送验证码与 Turnstile）V1 留给之后的任务；验证记录 30 天后删除与超过阈值的运营告警邮件仍按 SHOP-TASK-069 记录段。上线前运营者须开通 Twilio Verify 与 Turnstile 并填写私有配置，并确认边缘反向代理为本站设置 `X-Real-IP`（来源限流依赖它，见 `client_source`）。
- 验证到什么程度：人工逐条对照验收标准、DESIGN 1.11 与 HANDOFF 0.41 的决定原句自查。`tests/test_sms_api.py` 用 `TestClient` 与 SQLite 内存库（引擎设置与 `tests/test_sms_verification.py` 相同，另允许跨线程用同一连接），会话依赖换成绑定同一内存库的会话，服务商与人机挑战用 SHOP-TASK-067 的替身（服务商另加逐次不同的请求 ID），`get_sms_redis_client` 换成内存替身 FakeRedis 或不覆盖；每条测试的文档字符串写明它守住的设计原句、Kelvin 决定或验收条目。覆盖：发送成功 200 与记录、四种用途、号码按地区规范化（含以加号开头时以输入为准）、来源取 `X-Real-IP`；七种结果的状态码与错误体（开关关闭含无设置行、白名单外、人机挑战未通过与服务不可用、按号码 60 秒限流、无法送达、服务商不可用、Redis 出错），开关关闭与白名单外时人机挑战、限流、服务商都未调用且不写记录；MySQL 出错（以替换开关读取函数抛出带号码参数的 `OperationalError` 模拟）与结算时 `SmsBudgetError`（第二个事务回滚、不留记录）都为 503 `sms_suspended` 且不含号码；数据库未配置时 503 `database is not configured`；Redis 依赖在未配置与连接串不对时返回 `None`、配置时返回客户端，不覆盖依赖时为 503 `sms_suspended`（不是 `service_unavailable`）且开关、白名单与人机挑战仍先判定、服务商未调用；登录与重设用途下已注册与未注册号码的状态码、响应头与响应体相同；413 在 4 KB 恰好放行、多 1 字节拒绝，分块发送时也按实际字节、先于 415 与 422；415 先于 422；JSON 媒体类型可带参数；缺字段、多出字段、类型不对、令牌为空或超过 2048 个字符、未知用途（含 `delete_account` 与大写）、请求体不是对象、JSON 不合法都为 422 且只有位置、类型与消息，不回显请求内容，人机挑战、限流与服务商都未调用；2048 个字符的令牌放行；号码与地区代码不成立为 `phone_invalid`；405 不含请求内容；无应用日志，任何日志都不含号码与令牌；全部响应（405 除外）带 no-store。未连真实的 Twilio Verify、Turnstile、Redis 或 MySQL。这些测试只由 PR 的必需 CI 检查 backend 执行。检查命令结果由 Worker 另行记录。
