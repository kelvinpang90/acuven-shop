# SHOP-TASK-190 后台商品图片的上传、调序与移除接口

- [x] 依据：`docs/DESIGN.md` 1.19（提交 `6e8f655`）「计价、优惠、积分与库存」第 13 条「上传」的检查顺序；`docs/UX.md` 0.17 的 A04 图片部分（上传、排序与移除各自立即生效，成功后显示服务端返回的图片列表，被拒时按服务端的回答显示）；`docs/HANDOFF.md` 0.79 的落实写法（上传路径与反向代理放宽到 6m 的 `^/api/admin/products/[0-9]+/images$` 一致；错误的 detail 与 UX-COPY 0.18 的键同名；5 MB 指 5,242,880 字节；三个接口成功都回答 `images`；处理函数为同步函数）。设计闸门：DESIGN 1.19（提交 `6e8f655`）第 13 条与 HANDOFF 0.79。本任务只做后台接口层，把 SHOP-TASK-188 的 `process_image` 与 SHOP-TASK-189 的服务层接成接口；不做前端，不改服务层、模型与设计。提供接口为 SHOP-TASK-191，页面 A04 另行登记。
- [x] 新增 `app/api/admin_product_images.py`（路由类为 SHOP-TASK-027 的 `_NoStoreRoute`，处理函数与依赖产生的全部响应都带 `Cache-Control: no-store`），在 `app/main.py` 注册：
  - `POST /api/admin/products/{product_id}/images`（上传），检查依次为，前一项不通过即回答、不再往下：`require_admin`（401 `admin_session_required`）→ X-CSRF-Token（403 `csrf_failed`）→ 路径 ID（沿用 `admin_products` 的 `_product_id`，不合法 422）→ `load_product_images` 为 None 即 404 `product_not_found` → `image_store_configured` 为 False 即 503 `image_store_unavailable`、不读请求体 → Content-Type 去掉分号后的参数与首尾空白、转小写后不是 `image/jpeg`、`image/png`、`image/webp` 之一即 415 `image_type_unsupported` → 请求头声明的长度超过 5,242,880 即 413 `image_too_large`、不读请求体 → 最后声明的异步依赖以 `request.stream()` 逐块读取，读到超过即停止并 413 → 已有 8 张即 409 `images_full` → `process_image` 抛 `ImageRejected` 即 422 `image_invalid` → `add_image`：`ImagesFull` 409 `images_full`、`ProductMissing` 404 `product_not_found`、`ImageStoreUnavailable` 503 `image_store_unavailable`。成功 201 与 `images`。
  - `PUT /api/admin/products/{product_id}/images`（调序）：请求体经 `app/api/pay.py` 的 `_json_body` 逐块读取（上限 8 KB，413 `request body too large`；不是 JSON 415 `request body must be JSON`），先于会话检查 → `require_admin`（401）→ CSRF（403）→ 路径 ID（422）→ 请求体结构（`{"image_ids": [整数…]}`，strict，多出字段、缺字段、null 或类型不对 422，经 `_body_errors` 不回显）→ `reorder_images`：`ProductMissing` 404 `product_not_found`、`ImagesChanged` 409 `images_changed`。成功 200 与 `images`（顺序未变时服务层不写库、不写审计，同样 200）。
  - `DELETE /api/admin/products/{product_id}/images/{image_id}`（移除）：`require_admin`（401）→ CSRF（403）→ 商品 ID 与图片 ID（写法同 `_product_id`，图片 ID 的错误为 `path.image_id`、类型 `image_id_invalid`，不合法 422）→ `remove_image`：`ProductMissing` 404、`ImagesChanged` 409 `images_changed`；存储未配置时照常移除（服务层只记日志）。成功 200 与 `images`。
  - 响应为 `{"images": [{"id", "storage_ref"}…]}`（`load_product_images` 的列表，项沿用 `admin_products` 的 `ImageOut`）。三个处理函数都是同步函数，FastAPI 在线程池里执行，`process_image` 与 R2 调用不阻塞事件循环；只有读请求体的依赖是异步的。不写日志（服务层与存储模块自己的日志除外）。
- [x] `tests/test_admin_products_api.py` 的 `test_routes_are_the_four_endpoints`：路径筛选排除以 `/images` 结尾与 `/images/` 之下的路径，四个期望路由不变；该文件其他测试未改。
- [x] 测试：新增 `tests/test_admin_product_images_api.py`，夹具照 `tests/test_admin_products_api.py`（StaticPool、关闭 check_same_thread、开外键、https 的 base_url，以 `issue_admin_session` 登录）；`Settings` 以四个原名构造为已配置，未配置的用例不传；时间以 monkeypatch 本接口模块与 `app.api.admin_auth` 的 `_utcnow` 固定；`app.services.image_store` 的 `put_image` 与 `delete_image` 以 monkeypatch 替换；上传样本用 Pillow 现场生成 300×300 的 PNG。每条测试的文档字符串写明它守住的第 13 条、A04 原句或验收约定。覆盖：上传成功 201、列表、写入存储的是 WebP、行的格式与尺寸、审计、版本号不变；Content-Type 的参数、大小写与空白，以及声明与内容不一致时以内容为准；检查顺序——未登录 401 先于一切、CSRF 403 先于路径 ID、路径 ID 422、商品不存在 404 先于存储未配置的 503、未配置 503 不调用 `put_image`（类型不对、声明过大、已满时也是 503）、415 先于 413、声明长度 5,242,881 的 413（实际只有一张合格的 PNG，已满时也是 413）、未声明长度时读到超过即 413、恰好 5,242,880 字节不算太大、已有 8 张时即使请求体不是图片也回 409 `images_full`、坏图（非图片、空、截断、199×199）422 `image_invalid`、写入失败 503；调序的成功与审计、顺序未变不写、409 `images_changed`（漏列、重复、别的商品、不存在、空数组）、404、请求体 422 不回显、413 与 415 先于会话；移除的成功（删行、删对象、审计）、存储未配置照常移除、409 `images_changed`（别的商品、不存在、已移除）、404；所有响应带 no-store、应用不记日志；路由只有这三个，上传路径符合反向代理放宽的那一条。
- 偏离与取舍：
  - 上传的检查拆成依赖，按声明顺序完成（照 `admin_products` 先声明会话与 CSRF、再声明路径 ID）：商品存在、存储已配置、Content-Type 与声明长度四项合在一个同步依赖 `_upload_target` 里依次判断（都只看请求头与数据库、不读请求体），请求体由最后声明的异步依赖 `_image_body` 读取。这样 404、503、415 与声明过大的 413 都在读请求体之前回答。
  - 「已有 8 张」用 `_upload_target` 里 `load_product_images` 读到的列表判断，排在读完请求体之后、`process_image` 之前（设计的顺序）；读请求体期间若被别处加满，由 `add_image` 锁行后的计数兜底，同样回 409 `images_full`。
  - Content-Length 不是十进制整数时按未声明处理，由逐块读取把关（这种请求通常在服务器层就被拒绝）。
  - 413 与 415 的 detail 按 HANDOFF 0.79 只对上传用 UX-COPY 的键；调序的请求体上限与 JSON 判断沿用现有接口的 `request body too large` 与 `request body must be JSON`（契约写「照 `_write_body`」），上限 8 KB 直接复用 `app/api/pay.py` 的 `_json_body`（8 KB）。
  - 图片 ID 的上限沿用商品 ID 的 `MAX_PRODUCT_ID`（INT 上限，与服务层的 `MAX_ROW_ID` 相同）。
  - 404 `product_not_found` 与 503 `image_store_unavailable` 不是 UX-COPY 的键，页面照其他失败显示（HANDOFF 0.79）。
- 验证范围：上面列出的是本次新增与修改的测试代码，存储函数全部替换、不访问 R2；结果以 PR 的必需 CI 检查 backend 为准。
