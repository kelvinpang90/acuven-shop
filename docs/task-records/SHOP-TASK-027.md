- 接口与字段（三个接口都不读会员会话；订单号与电话只在请求体里，不进任何路径或查询参数；所有响应含错误都带 `Cache-Control: no-store`）：
  - `POST /api/orders/lookup`：请求体只有 `order_number` 与 `phone` 两个字符串。通过时 204、响应体为空，签发该单 `lookup` 范围的授权并设置 SHOP-TASK-019 的 cookie `__Host-shop_order_access`（沿用本浏览器的会话时以原值重设，刷新 Max-Age）。查单不改订单状态，任何状态的订单（含待支付与已取消）都可查。
  - `GET /api/orders/lookup?lang=en|zh|ms`（默认 `en`，取值与目录接口相同）：`{"orders": [...], "csrf_token": "<由 cookie 重新算出>"}`，订单是本浏览器当前有效的 `lookup` 授权所对应的订单（`list_order_access`），按授权到期时间从晚到早；返回前先对其中待支付的订单执行 SHOP-TASK-021 的 `expire_overdue_orders`。每张订单：`order_number`、`status`、`created_at`、`paid_at`（未支付为 null）、`server_time`（时间都是带 `Z` 的 UTC）、`lines`（每行 `name`、`variant_label`、`quantity`、`unit_price_sen`、`line_subtotal_sen`、`unit_cash_paid_sen`（逐件实付金额，按件序），按请求语言取下单时的快照，按行序）、`subtotal_sen`、`shipping_fee_sen`、`total_sen`、`recipient`（`name`、`phone`、`country_code`、`region`、`address`、`postal_code` 原文；没有收货资料记录时为 null）。不返回优惠券与积分两项（现有订单都是游客订单，按 `docs/UX.md` 0.7 的 P09 游客订单不显示这两行；会员任务扩展）。
  - `POST /api/orders/confirm-receipt`：请求头 `Idempotency-Key`（规则同 SHOP-TASK-020）与 `X-CSRF-Token`；请求体只有 `order_number`（按页面从查看接口取得的规范写法，不做查单那样的规范化）。新写与按幂等键重放都是 200 `{"status": "<订单状态>"}`。
- 查单的处理顺序（每一步不通过即停止）：逐块读请求体，超过 8 KB 即 413（先于一切校验）→ 不是 `application/json` 即 415 → 请求体校验，多出字段或不是字符串即 422 → 取 Redis 客户端 → 用 SHOP-TASK-026 的 `hit` 按 `client_source` 计一次（桶 `order_lookup_source`，10 分钟窗口上限 30 次，成功失败都计），超过 429 → 订单号去掉空格与连字符、转大写，再把 I、L 换成 1、O 换成 0，用 SHOP-TASK-010 的 `is_valid_order_number` 检查 → 用 `current_count` 读规范化订单号的失败计数（桶 `order_lookup_failures`），已达 10 次即 429（电话正确也拒绝）→ 按订单号查订单与收货电话，用 SHOP-TASK-011 的 `normalize_phone`（默认地区 `MY`，以加号开头时以输入为准）规范化电话，以 `hmac.compare_digest` 与该单收货电话比对 → 订单不存在、电话无法规范化或不符时用 `hit` 给该订单号的失败计数加一（1 小时窗口）后 404 → 通过时在同一事务里用 `issue_order_access` 签发 `lookup` 授权并提交。
- 确认收货的处理顺序（每一步不通过即停止且不读写订单数据）：请求体大小与格式（413、415，幂等键与请求体一并校验 422）→ 按订单号查订单 ID，以当前 cookie 与 `lookup` 范围调用 `check_order_access`（订单号格式不对或不存在、授权过期、不属于该会话或范围不符一律同一个 401）→ `check_csrf_token`（403）→ 才查幂等键与订单状态。
- 错误码：404 `{"detail": "not_found"}`（`lookup.not_found`；订单号格式不合法、订单不存在、电话无法规范化与电话不符的状态码、响应体与响应头完全相同）；429 `{"detail": "rate_limited"}`（`common.rate_limited`）；503 `{"detail": "service_unavailable"}`（`common.service_unavailable`；Redis 连接串未配置、连不上或超时，发生在来源计数或读失败计数时不查订单，发生在失败计数加一时返回同一个 503 而不是 404、不签发授权）；401 `{"detail": "access_expired"}`（`order.session_expired`）；403 `{"detail": "csrf_failed"}`；409 `{"detail": "idempotency_conflict"}` 与带订单当前状态的 `{"detail": "order_not_confirmable", "status": "<当前状态>"}`；413、415、422（每条错误只有 `type`、`loc`、`msg`，不回显请求内容）。
- 授权范围：`lookup` 授权不能用于 SHOP-TASK-021 的支付与取消接口（它们只认 `guest_checkout`，未改）；`guest_checkout` 授权不能用于本任务的查看与确认收货。
- 确认收货：
  - 幂等：指纹是 `{"order_id": <订单 ID>}` 的 JSON（键排序、无空白）的 SHA-256 `hexdigest`；先按幂等键查确认收货记录，指纹相同（常量时间比较）返回 200 与订单当前状态，不同 409 `idempotency_conflict`，都不改订单。
  - 订单为 `demo_shipped` 时，经 `is_transition_allowed(demo_shipped, demo_completed, guest)` 检查后，同一事务里先写确认收货记录（操作者 `guest`），再 `UPDATE orders SET status = 'demo_completed' WHERE id = ? AND status = 'demo_shipped'`，写一条操作者 `guest` 的事件，提交后 200 `{"status": "demo_completed"}`。其他任何状态（含已经 `demo_completed`）409 `order_not_confirmable` 与当前状态，不写记录与事件。
  - 写记录撞上唯一约束（同键，或同一订单已有记录）或条件 UPDATE 未命中时回滚，再按幂等键重新查询：同键同指纹返回原结果，同键不同指纹 409 `idempotency_conflict`，否则 409 `order_not_confirmable` 与当前状态。订单 ID 的唯一约束保证一单至多一次手动确认、不出现一单两次完成。
- 确认收货记录表 `receipt_confirmations`（`ReceiptConfirmation`，不存任何个人资料）：`id` 主键；`order_id` 非空、外键到 `orders.id`（`ON DELETE RESTRICT`）、全表唯一；`idempotency_key` `VARCHAR(64)` 非空、全表唯一；`request_fingerprint` `VARCHAR(64)` 非空；`actor_type` `VARCHAR(10)` 非空；`created_at` 不带时区的 UTC `DATETIME` 非空。约束名：`pk_receipt_confirmations`、`fk_receipt_confirmations_order_id_orders`、`uq_receipt_confirmations_order_id`、`uq_receipt_confirmations_idempotency_key`；检查约束 `ck_receipt_confirmations_idempotency_key_not_empty`（`LENGTH(idempotency_key) >= 1`）、`ck_receipt_confirmations_request_fingerprint_length`（`LENGTH(request_fingerprint) = 64`，沿用 `orders` 与 `payment_attempts` 的写法，只约束长度，十六进制由服务层生成保证）、`ck_receipt_confirmations_actor_type_valid`（`actor_type IN ('guest', 'member')`）；表选项 `ENGINE=InnoDB`、`DEFAULT CHARSET=utf8mb4`。迁移 revision `0011`、down_revision `0010`，upgrade 建表、downgrade 删表；订单 ID 的唯一约束兼作订单外键在 MySQL 上的索引，不另建普通索引。
- 留给之后的任务（本任务都不预留参数）：全部退款后冻结确认收货由之后的退款任务扩展本任务的确认路径；模拟发货满 7 天自动完成由之后的定时任务负责（操作者 `system`，不写确认收货记录）；会员凭会话访问与确认收货（记录的操作者 `member`）由之后的会员任务扩展。
