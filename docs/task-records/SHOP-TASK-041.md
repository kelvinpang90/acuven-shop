# SHOP-TASK-041 后台退款审核 API

- [x] 按 `docs/DESIGN.md` 1.11（提交 `2d13250`）「订单与退款状态」（`requested` → 管理员 `approved` 或 `rejected`；已批准的退款不可再次批准；系统显示累计已退及剩余可退金额；示例运费始终不退）、「权限与资料保护」（仅管理员可见所有订单原始资料；后台单一管理员也须认证；日志不记录姓名、完整电话、地址与订单查询参数）、「失败、并发与重试」第 1 条（审核使用幂等键和数据库唯一约束）与 `docs/HANDOFF.md` 0.33 记录的 Kelvin 2026-10-06 退款审核决定，用 SHOP-TASK-040 的规则函数提供退款申请列表、详情、批准与拒绝四个接口（A03 的后端）：列表与详情在新文件 `app/services/admin_refunds.py`，接口在新文件 `app/api/admin_refunds.py`（`app/main.py` 挂上路由）；测试见 `tests/test_admin_refunds.py`。字段参照 `docs/UX.md` 0.8 的 A03。未做页面、积分返还与追回，未加表或迁移，未改 SHOP-TASK-029、036、040 的已有函数与测试、前端、`.platform/`、CI、部署配置或设计，未装依赖。设计闸门：DESIGN 1.11（提交 `2d13250`）。拆分：接口层。
- 接口（处理函数与依赖产生的全部响应，含错误，都带 `Cache-Control: no-store`，沿用 SHOP-TASK-027 的路由类 `_NoStoreRoute`；路径存在但方法不匹配的 405 由框架回答，不在此列。四个接口都经 SHOP-TASK-036 的 `require_admin`；路径只用退款申请的内部整数 ID，订单号与收货资料不进任何路径或查询参数，唯一的查询参数是语言 `lang`）：
  - `POST /api/admin/refunds/query?lang=en|zh|ms`：只读，不要求 CSRF，不写审计。请求体只有可选的 `status`（`requested`、`approved`、`rejected` 之一或 null）与 `page`（1 到 10000 的整数，默认 1），多出字段 422。返回 `{"total": 符合条件的总数, "page": 页码, "page_size": 20, "refunds": [...]}`，每行 `id`、`created_at`（申请时间）、`order_id`（所属订单的内部 ID）、`order_number`、`status`、`amount_sen`（申请金额，整数仙）与 `lines`（按订单行序，每行 `name` 按语言参数取的商品名称快照、`quantity` 申请件数）；不含收货资料与理由。
  - `GET /api/admin/refunds/{refund_id}?lang=en|zh|ms`（语言参数同目录接口，默认 `en`）：返回 `id`、`status`、`created_at`、`reviewed_at`（未审核为 null）、`reviewer_username`（未审核为 null）、`review_reason`（只在后台返回；未审核或批准时没写理由为 null）、`order_id`、`order_number`、`order_status`、`amount_sen`、`lines`（按订单行序，每行 `name`、`variant_label`、`quantity` 申请件数、`purchased_quantity` 该行购买件数、`approved_quantity` 该行被已批准申请占用的件数）、`refunded_sen` 与 `refundable_left_sen`（该单累计已退与剩余可退，取自 SHOP-TASK-029 的 `refund_state`）与 `csrf_token`（由后台会话 cookie 经 SHOP-TASK-035 的 `csrf_token_for_cookie` 算出）；不含收货资料，不写审计。时间都是带 `Z` 的 UTC。
  - `POST /api/admin/refunds/{refund_id}/approve` 与 `POST /api/admin/refunds/{refund_id}/reject`：须带 `Idempotency-Key`（规则同 SHOP-TASK-020：恰好一个，16 到 64 个字母、数字、连字符或下划线）与 `X-CSRF-Token`（经 SHOP-TASK-036 的 `require_admin_csrf`）。请求体只有 `reason`（字符串或 null；批准可省略或为空，拒绝必填），多出字段 422。调用 SHOP-TASK-040 的 `approve_refund` / `reject_refund`，成功后提交；新审核与同键同请求重放都是 200 `{"refund_request_id", "status", "reviewed_at", "review_reason"}`（SHOP-TASK-040 的 `ReviewOutcome`，`status` 为申请当前状态）。
- 批准与拒绝的检查顺序（每一步不通过即停止）：逐块读请求体，超过 8 KB 即 413 → 不是 `application/json` 即 415 → `require_admin` 401 → CSRF 403 → 路径里的申请 ID、`Idempotency-Key` 与请求体一并校验 422 → 之后才调用规则函数（理由不合法 422 `reason_invalid`，在读取申请之前；申请不存在 404；幂等与已审核判断见下）。列表：413 → 415 → 请求体 422 → `require_admin` 401 → 语言参数 422。详情：`require_admin` 401 → 路径里的申请 ID 422 → 语言参数 422 → 申请不存在 404。
- 错误码：401 `admin_session_required`、403 `csrf_failed`、404 `not_found`、422 `reason_invalid`（不回显理由）、409 `idempotency_conflict`（同键不同内容：不同理由、相反结果或另一笔申请）、409 `refund_already_reviewed`（用新键审核已审核的申请，另带申请当前状态 `status`）。这些错误体都是 `{"detail": "<错误码>"}`（409 已审核另有 `status`）。413、415 与现有接口相同（`request body too large`、`request body must be JSON`）。请求结构、幂等键、语言参数与路径 ID 的 422 的 `detail` 是错误列表，每条只有 `type`、`loc`、`msg`，不回显请求内容：请求体同 `app/api/pay.py` 的 `_body_errors`，幂等键同 `app/api/orders.py` 的 `_key_errors`（缺失时 `{"type": "missing", "loc": ["header", "Idempotency-Key"], "msg": "Field required"}`，与游客下单相同），语言参数同 `_language`，路径里的申请 ID 自行校验（只接受不带符号与前导零、不超过 2147483647 的十进制整数，否则 `{"type": "refund_id_invalid", "loc": ["path", "refund_id"], "msg": "Refund request ID should be a positive integer"}`）。
- 排序与分页：按申请时间从新到旧、同一时间按申请 ID 从大到小，每页 20 条（沿用 `app/services/admin_orders.py` 的 `PAGE_SIZE`），`page` 超出时 `refunds` 为空、`total` 照常；可按状态筛选。
- 审计：只有实际改变状态的批准与拒绝写审计，由 SHOP-TASK-040 的规则函数写（`admin_refund_approved` / `admin_refund_rejected`，不写理由原文）；列表、详情、重放、409、403、404、422 都不写。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题；Kelvin 2026-10-06 的决定与 DESIGN 1.11 一致）：
  - UX A03 的详情有 `[admin.refund_points]`（M2：返还抵扣积分与追回获得积分）。现有订单都是游客订单，积分返还与追回等会员与积分账本任务接入，本任务按验收不返回任何积分字段；之后由那个任务补上。
  - UX A03 列表有「订单号」列，所以列表返回 `order_number`（只在响应体里，不进路径或查询参数）；同时返回所属订单的内部 ID `order_id`，供页面跳到 A02 的详情接口。
  - 列表的语言放在查询参数 `lang`（同目录接口），请求体仍只有状态与页码。
  - 列表的请求体 422 先于 401（请求体依赖写在会话依赖之前，与 SHOP-TASK-037 的列表相同；验收只规定 413 先于其他校验）；批准与拒绝按验收的固定顺序，结构与幂等键的 422 在 CSRF 之后。路径里的申请 ID 不合法与幂等键、请求体的错误一并在 CSRF 之后回答；详情的路径 ID 在会话之后校验。
  - 理由是否必填与长度由规则函数判断（`reason_invalid`），请求模型只约束「字符串或 null」：拒绝时缺省或为 null 也是 `reason_invalid`，而不是结构 422。理由超过 500 个字符不另设模型上限（请求体已有 8 KB 上限）。
  - `approved_quantity` 是该订单行被所有已批准申请占用的件数（含本申请，若它已批准），不是本申请的件数。
  - 规则函数抛出异常时接口立即回滚，释放订单行的锁；重放没有改动，也照常提交（只结束事务）。
  - 接口与依赖不写日志；错误响应不含订单号、理由、收货资料、用户名或令牌。未预期异常的 500 由框架在路由之外回答，不在 no-store 范围内（与 SHOP-TASK-036、037 相同）。
