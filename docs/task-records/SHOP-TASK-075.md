# SHOP-TASK-075 短信验证后登录或注册与认领游客订单规则

- [x] 按 `docs/DESIGN.md` 1.11（提交 `2d13250`）「权限与资料保护」第 1、2、3 条（注册、短信登录与结账验证是同一个短信验证流程：验证通过后号码已注册则登录，未注册则创建无密码会员并登录，随后自动认领该号码近 30 天、未认领的游客订单；每个游客订单只能认领一次）与「计价、优惠、积分与库存」第 3 条（认领过去游客订单不追发积分），在 SHOP-TASK-069 的 `verify_code` 与 SHOP-TASK-071 的 `issue_member_session` 之上新建 `app/services/member_sms_login.py`；测试见 `tests/test_member_sms_login.py`。未做接口与会话 cookie，未加表或迁移，未改 `app/services/sms_verification.py`、`app/services/member_auth.py`、模型、`.platform/`、CI、部署配置或设计，未装依赖。设计闸门：DESIGN 1.11（提交 `2d13250`）与 HANDOFF 0.41（会员注册登录与个人资料）。拆分：业务规则层（3 个允许路径）。
- 用途与入参（`sms_login_or_register(db, provider, phone_e164, purpose, code, now) -> SmsLoginResult`）：用途只接受 `checkout`、`register`、`login`（`SMS_LOGIN_PURPOSES`，三者走同一流程），其余（含 `reset_password`、`delete_account`）抛消息固定的 `ValueError`；`now` 带时区抛 `ValueError`（同 `member_auth`）；号码不是规范化 E.164 时由 `phone.is_sms_whitelisted` 抛 `InvalidPhoneNumber`（只用来校验格式，不看是否属于白名单）。三者都在核验之前，不调用服务商、不写库。
- 核验：调用 `verify_code`；结果不是 `approved`（`wrong_code`、`expired`、`unavailable`、`no_pending`、`sms_disabled`）时原样放在返回结果里，不查会员、不建会员、不认领、不签发会话。开关在流程途中被关闭由 `verify_code` 的 `sms_disabled` 保证。
- 登录或注册：按号码找 `status` 为 `active` 的会员，找到即登录（密码哈希不变）；找不到即在保存点（`begin_nested`）里创建 `active`、无密码哈希、创建时间为 `now` 的会员。撞上 `members` 的号码唯一约束（并发注册同一号码）时保存点回滚（之前 flush 的核验记录保留），以加锁读（`with_for_update`，MySQL 上为 `SELECT … FOR UPDATE`，SQLite 上不生成）改读已存在的 `active` 会员登录；加锁读仍找不到时按数据库错误处理（不建会员、不签发会话）。已注销的会员号码已清空，不会被找到，同号重新验证即创建新会员。
- 认领：一条条件 UPDATE——订单 ID 在「收货电话等于该号码」的 `order_recipients` 子查询里、`claim_status` 为 `open`、`member_id` 为空、`now - 30 天 <= created_at <= now`（`CLAIM_WINDOW`，两端都含，创建时间晚于 `now` 的不认领，写法同 `verify_code` 的 10 分钟窗口），不论订单状态；把 `member_id` 设为该会员、`claim_status` 改为 `claimed`，返回条数为本次认领的订单数。`claimed` 与 `not_claimable` 的订单（含注销后 `member_id` 已清空的）不被改到，同一订单不会被认领两次。不发积分、不写订单事件、不改订单状态与收货资料、不碰订单访问会话与授权。每次核验通过都执行一次（登录与新注册相同）。
- 签发与事务：认领之后以 `issue_member_session` 签发会话。返回 `SmsLoginResult(verification, member, issued, claimed_orders, created_member)`，`member` 与 `issued` 为 `repr=False`；核验不通过时两者为空、条数为 0、`created_member` 为假。全程只 flush、不提交：核验记录改为 `approved`、会员、认领与会话由调用方在同一个事务里提交。`verify_code` 的 `SmsVerificationError` 原样交给调用方；查会员、建会员、认领与签发时的 `SQLAlchemyError`（以及加锁读仍找不到会员）换成消息固定为 `member sms login storage failed` 的 `MemberSmsLoginError`（`RuntimeError` 子类），在 except 块之外抛出、不挂原异常；两种情况都由调用方回滚。不写日志。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 验收之外另拒带时区的 `now`（`issue_member_session` 本来也会拒，提前到核验之前，免得核验已通过才失败）。
  - 签发会话也放在转换数据库错误的范围里（验收只列了查会员、建会员与认领）；签发的 INSERT 不含号码，放进来只是让调用方只需处理一种本函数自己的异常。
  - 认领的条件 UPDATE 用 `synchronize_session=False`（写法同 `verify_code` 的条件更新），调用方会话里已加载的 `Order` 对象不随之刷新。
  - 号码格式借 `is_sms_whitelisted` 校验、丢弃其结果：白名单外但格式成立的号码照常交给 `verify_code`，它没有待核验记录，结果为 `no_pending`。
- 留给之后的任务：短信登录或注册接口、会员会话 cookie 与退出（SHOP-TASK-076）；结账会员路径在验证通过后以会员身份继续结账（短信验证组件 V1 与结账会员路径）；密码重设与注销确认用途的核验在各自任务里接上。
- 验证到什么程度：人工逐条对照验收标准与 DESIGN 1.11 原句自查。`tests/test_member_sms_login.py` 用 SQLite 内存库按模型建表（引擎设置与 `tests/test_sms_verification.py` 相同，由引擎发 BEGIN，保存点与 MySQL 上一样），服务商用 SHOP-TASK-067 的 `FakeSmsProvider`（另加一个核验时抛异常的子类），验证记录、会员与订单直接写库；每条测试的文档字符串写明它守住的设计原句或验收条目。覆盖：三个用途走同一流程（建会员、认领、记录改为 `approved`）；`reset_password`、`delete_account`、未知与大写用途抛 `ValueError` 且不调用服务商；五种不是规范化 E.164 的号码抛 `InvalidPhoneNumber`、不核验、不写库；带时区的时间被拒；五种非 `approved` 结果都不建会员、不签发会话、不认领（`no_pending` 与 `sms_disabled` 不调用服务商），验证码错误时不登录已注册会员；服务商异常以 `SmsVerificationError` 原样交出且不含号码与验证码；已注册号码（有密码与无密码）登录原会员、密码哈希不变；未注册号码新建 `active`、无密码哈希、创建时间为当前时间的会员；撞上号码唯一约束（包住查找函数，在第一次不加锁的查找之后、插入之前直接写入同号会员模拟）时登录对方的会员、记录仍为 `approved`、只有一个会员、加锁读按 MySQL 方言编译带 `FOR UPDATE` 而第一次查找不带；加锁读仍找不到时抛不含号码、不挂原异常的 `MemberSmsLoginError`，回滚后不多出会员与会话；已注销会员同号重新验证得到新会员，旧会员的 `claimed` 订单不被再次认领；认领窗口恰满 30 天与当前时间认领、早一秒与晚于当前时间一秒不认领；四种订单状态的 open 订单都认领，其他号码、`claimed`（有会员与已清空）、`not_claimable`（有会员与已清空）的订单不变；第二次验证通过不重复认领、只认领之后新出现的订单，第三次为 0；认领后订单除会员 ID 与认领状态外每列不变（含获得积分与状态），收货资料、订单事件、订单访问会话与授权不变；签发的会话能被 `check_member_session` 校验通过、30 天到期；函数返回后回滚，会员、认领与会话都不存在、记录仍为 `sent`；认领时数据库异常（带号码参数）换成不含号码与 SQL、不挂原异常的异常；返回结果的 repr 不含号码、验证码、密码哈希与令牌；不产生日志记录。并发只在同一会话里以替换查找函数模拟，MySQL 上两个事务的实际交错、唯一约束等待与加锁读未在真实 MySQL 上验证；未连真实的 Twilio Verify。这些测试只由 PR 的必需 CI 检查 backend 执行，Worker 沙箱不跑 pytest。检查命令结果由 Worker 另行记录。
