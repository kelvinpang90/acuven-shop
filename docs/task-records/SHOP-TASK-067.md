- 配置项（前缀 `SHOP_`，默认都是空串即未配置，变量名与 `.env.example` 已登记的六项一致）：`twilio_account_sid`、`twilio_auth_token`、`twilio_verify_service_sid`、`twilio_verify_base_url`（只写到主机，如 `https://VERIFY_API_HOST`，路径由适配器拼接，末尾斜杠去掉）、`turnstile_secret_key`、`turnstile_verify_url`（完整网址，含路径）。Twilio 四项缺一、Turnstile 两项缺一，或接口地址不以 `https://` 开头，都视为未配置：调用一律归为 `unavailable`、不调用传输函数（未配置的判断在号码、令牌等输入的校验之前）。
- 传输（`sms_provider.py`，`captcha.py` 从这里引入）：`Transport` 是 `HttpRequest(url, form, headers) -> HttpResponse(status, body)` 的可调用对象，非 2xx 也作为响应返回，超时与网络错误抛 `TransportError`（消息固定为 `provider request failed`，`from None` 不带原异常链）。默认的 `urllib_transport` 以标准库 urllib 发一次 POST：请求体为 `application/x-www-form-urlencoded`，带 `Accept: application/json`；`timeout=5`（urllib 的套接字超时，建立连接与之后每次读取各自最多 5 秒）；不重试；地址不是 `https://` 时不发请求、抛 `TransportError`；不跟随重定向（跟随会把认证头带到别的地址，3xx 作为响应返回）；响应体最多读 64 KiB。适配器把 `TransportError` 与 `OSError` 都归为 `unavailable`，异常不外抛。
- Twilio Verify（`TwilioVerifyClient`，协议 `SmsProvider`）：
  - 发起 `start_verification(phone_e164) -> SendResult(status, request_id)`：`POST {base}/v2/Services/{服务 SID}/Verifications`，表单 `To`、`Channel=sms`，`Authorization: Basic base64(账号 SID:令牌)`。号码须为规范化 E.164（`+` 加首位非 0 的 2–15 位数字），否则抛 `ValueError`（编程错误，消息不含号码，不发请求）。2xx 且 JSON 里 `status` 为 `pending`、`sid` 为 `VE` 加 32 位十六进制时为 `accepted`（带该 `sid`）；非 2xx 时按错误码表 `START_ERROR_CODES` 归类：21211、60200（无效号码；本适配器只传 `To` 与固定的 `Channel`，参数无效只会因 `To` 而来）、21612、21614、60205（不能收短信）、21408、60410、60605（不支持该目的地或被提供方拦截）为 `undeliverable`（不带请求 ID）；20003（认证失败）、20404（服务 SID 不对）、20429（限流）、60203（提供方对号码限流）及表外错误码、缺错误码、非 JSON、5xx 都为 `unavailable`。2xx 但非 JSON、缺 `sid` 或 `status`、`sid` 格式不对或 `status` 不是 `pending` 也为 `unavailable`。
  - 核验 `check_verification(request_id, code) -> CheckStatus`：`POST {base}/v2/Services/{服务 SID}/VerificationCheck`，表单 `VerificationSid`、`Code`，同样的认证头。2xx 按 `CHECK_STATUSES`：`approved` 且 `valid` 为 `true` 为 `approved`（`approved` 而 `valid` 不是 `true` 为 `unavailable`，不放行）；`pending` 为 `wrong_code`；`canceled`、`expired`、`max_attempts_reached`、`deleted`、`failed` 为 `expired`；表外或缺 `status` 为 `unavailable`。非 2xx 按 `CHECK_ERROR_CODES`：20404（Twilio 在验证通过、过期或尝试次数用尽后删除验证，再核验即找不到）、60202（尝试次数用尽）、60023（没有待核验的验证）为 `expired`；20003、20429、表外错误码、缺错误码、非 JSON 与 5xx 为 `unavailable`。
  - 两张错误码表与状态表都是模块常量，注释写明依据（Twilio 错误码字典与 Verify 的 Verification Check 文档）。
- Turnstile（`TurnstileVerifier`，协议 `CaptchaVerifier`）：`verify(token) -> CaptchaResult`，`POST` 到配置的核验地址，表单只有 `secret` 与 `response`，不带 `remoteip`，也不带其他请求头。令牌不是字符串、为空或超过 2048 个字符时为 `failed`、不发请求。2xx 且 `success` 为 `true` 为 `passed`；`success` 为 `false` 时按 `ERROR_CODES`：错误码全是令牌问题（`missing-input-response`、`invalid-input-response`、`timeout-or-duplicate`）为 `failed`；含密钥或请求问题（`missing-input-secret`、`invalid-input-secret`、`bad-request`）或 `internal-error`、表外错误码、错误码为空或缺失时为 `unavailable`。非 2xx、非 JSON、缺 `success` 或不是布尔值、超时与网络错误为 `unavailable`。
- 测试替身与依赖：`FakeSmsProvider(send_result, check_result)`（默认受理并带一个固定的 `VE…` 请求 ID、核验通过）与 `FakeCaptchaVerifier(result)`（默认 `passed`）按预设结果返回，只记调用次数（`send_calls`、`check_calls`、`calls`），不记号码、验证码或令牌，不发网络请求。`get_sms_provider(request)` 与 `get_captcha_verifier(request)` 按 `request.app.state.settings` 构造适配器（未配置时也返回实例，调用时归为 `unavailable`），供 SHOP-TASK-070 用作 FastAPI 依赖、测试以 `app.dependency_overrides` 换成替身；另有 `TwilioVerifyClient.from_settings`、`TurnstileVerifier.from_settings` 可传入传输函数。
- 不泄露：两个模块不写日志。返回值只有类别（与发起受理时的提供方请求 ID）；适配器、替身的 repr 只显示是否已配置或调用次数；`HttpRequest` 的地址、表单与请求头和 `HttpResponse` 的响应体都不进 repr；异常消息固定，不含号码、验证码、令牌、凭据或地址。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 允许改动的路径里没有单独的共用模块，传输函数放在 `sms_provider.py`，`captcha.py` 从那里引入。
  - 验收只列了 `unavailable` 的几种成因；表外的 4xx 错误码（及缺错误码的 4xx）也归为 `unavailable`（停发），不猜测为号码问题或验证码问题。
  - 核验状态 `deleted`、`failed` 不在验收列出的情形里，按「验证已结束、不能再核验」归为 `expired`（不降级为游客，与第 2 条「验证码错误或超过尝试次数不降级为游客」同向）；如应归 `unavailable` 须另行决定。
  - 本地先挡掉的两种输入不发请求：核验时请求 ID 不是 `VE` 加 32 位十六进制归为 `expired`（不可能存在），验证码不是 4–10 位数字（Twilio Verify 可设的长度）归为 `wrong_code`——此时并未向提供方确认验证仍待核验；也就不消耗提供方的尝试次数，调用方（SHOP-TASK-069）的尝试计数须自己算上这些。
