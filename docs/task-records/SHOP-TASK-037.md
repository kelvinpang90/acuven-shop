- 接口（处理函数与依赖产生的全部响应，含错误，都带 `Cache-Control: no-store`，沿用 SHOP-TASK-027 的路由类 `_NoStoreRoute`；三个接口都经 SHOP-TASK-036 的 `require_admin`；订单号与收货资料不进任何路径或查询参数，路径只用订单的内部整数 ID；不提供任何导出）：
  - `POST /api/admin/orders/query`：只读，不要求 CSRF，不写审计。请求体只有可选的 `order_number`（字符串或 null）、可选的 `status`（六种订单状态之一或 null）与 `page`（1 到 10000 的整数，默认 1），多出字段 422。返回 `{"total": 符合条件的总数, "page": 页码, "page_size": 20, "orders": [...]}`，每行 `id`（内部 ID）、`order_number`、`created_at`（下单时间）、`status`、`total_sen`（应付，整数仙）、`refunds_pending`（审核中的退款申请数）；不含收货资料。
  - `GET /api/admin/orders/{order_id}?lang=en|zh|ms`（语言参数同目录接口，默认 `en`）：返回 `id`、`order_number`、`status`、`created_at`、`paid_at`（未支付为 null）、`lines`（按行序，每行 `name`、`variant_label`、`quantity`、`unit_price_sen`、`line_subtotal_sen`、`unit_cash_paid_sen` 逐件实付列表）、`subtotal_sen`、`coupon_discount_sen`（券折扣）、`points_discount_sen`（积分抵扣，取订单的 `points_redeemed`，1 积分抵 1 仙）、`shipping_fee_sen`、`total_sen`、`recipient`（收货资料原文 `name`、`phone`、`country_code`、`region`、`address`、`postal_code`；没有收货资料记录时为 null）、`events`（每条 `created_at`、`status` 即迁移后状态、`actor_type`；按时间从早到晚、同一时间按事件 ID 从小到大；不含收货资料）、`refunds_pending`、`fully_refunded`（全部已退，冻结履约）与 `csrf_token`（由后台会话 cookie 经 SHOP-TASK-035 的 `csrf_token_for_cookie` 算出）。时间都是带 `Z` 的 UTC。
  - `POST /api/admin/orders/{order_id}/status`：请求体只有 `status`（只允许 `demo_packed`、`demo_shipped`），多出字段 422；须带 `X-CSRF-Token`（经 SHOP-TASK-036 的 `require_admin_csrf`）。推进或已是目标状态都返回 200 `{"status": 当前状态}`。
- 处理顺序（每一步不通过即停止）：两个 POST 接口先逐块读请求体，超过 8 KB 即 413（先于一切校验，含会话校验）→ 不是 `application/json` 即 415 → 请求体校验 422 → `require_admin` 401 →（推进）路径里的订单 ID 422 → CSRF 403（先于读取订单）→ 订单不存在 404 → 推进。详情：`require_admin` 401 → 路径里的订单 ID 422 → 语言参数 422 → 订单不存在 404 → 返回。
- 错误码（错误体 `{"detail": "<错误码>"}`）：401 `admin_session_required`、403 `csrf_failed`、404 `not_found`、409 `order_not_advanceable` 与 409 `fulfilment_frozen`（两者都另带订单当前状态 `status`）；413、415 与现有接口相同（`request body too large`、`request body must be JSON`）；422 的 `detail` 是错误列表，每条只有 `type`、`loc`、`msg`，不回显请求内容：请求体同 `app/api/pay.py` 的 `_body_errors`，语言参数同 `_language`，路径里的订单 ID 自行校验（只接受不带符号与前导零、不超过 2147483647 的十进制整数，否则 `{"type": "order_id_invalid", "loc": ["path", "order_id"], "msg": "Order ID should be a positive integer"}`）。
- 排序与分页（Kelvin 2026-10-05）：按下单时间从新到旧、同一时间按内部 ID 从大到小，每页 20 条，`page` 超出时 `orders` 为空、`total` 照常。订单号先按 SHOP-TASK-027 的 `normalize_order_number`（去掉空格与连字符、转大写、I/L 换 1、O 换 0）规范化，再与订单号精确比较；规范化后格式不合法时返回空列表而不是错误。可与状态筛选同时用。
- 审计（写入用 SHOP-TASK-035 的 `record_audit`，操作名常量定义在 `app/services/admin_orders.py`）：每次成功查看详情在同一请求里写一条 `admin_order_viewed`（对象类别 `order`、对象 ID 为内部 ID，不写旧值与新值）并在返回前提交；订单不存在不写。每次实际推进写一条 `admin_order_status_changed`（对象同上，旧值与新值为迁移前后的状态）。列表、已是目标状态、409、403、404 都不写审计。
- 推进规则：已是目标状态 → 200 与当前状态，不写事件与审计（重复点击安全）；否则以 SHOP-TASK-010 的 `is_transition_allowed` 与操作者 `admin` 检查（不允许跳过打包；待支付、已完成、已取消与倒退都不允许）→ 409 `order_not_advanceable`；再以 SHOP-TASK-029 的 `refund_state(...).fully_refunded` 判断全部已退 → 409 `fulfilment_frozen`（即使迁移本身允许）；通过时在同一事务里用带条件的 UPDATE（状态仍为检查时的状态才改）改状态、写一条操作者为 `admin` 的事件与一条审计并提交。
- 并发与锁定协议（也写在 `app/services/admin_orders.py` 的模块 docstring）：推进在同一事务里先以 `lock_order_statement`（`SELECT … FOR UPDATE`，即 SQLAlchemy 的 `with_for_update`）锁定该订单行，之后才读取当前状态与退款占用并判断；判断不通过时回滚释放锁。**之后的退款审核任务在批准退款前必须以同一查询锁定同一订单行，再读取退款占用并写入批准**，两者因此串行化，不会出现推进读到「未全部已退」而并发的批准同时把最后几件批准、两边都提交的情形。条件 UPDATE 另作兜底：未命中时回滚、重新读取订单，已是目标状态返回 200，否则 409 `order_not_advanceable` 与当前状态，不出现一单两次推进。
