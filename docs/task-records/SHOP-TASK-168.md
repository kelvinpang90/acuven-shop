- 短信服务是否可用：`app/api/admin_site_settings.py` 新增 `sms_service_configured(settings)`，只读传入的配置，不联网、不写日志，五类全部合格才为真：
  1. 短信服务商：`TwilioVerifyClient.from_settings(settings).configured`（四项非空，接口地址为 `https://`）；
  2. 人机挑战：`TurnstileVerifier.from_settings(settings).configured`（密钥非空，核验地址为 `https://`），且 `app/api/site_settings.py` 的 `turnstile_site_key(settings.turnstile_site_key)` 不为 None（公开接口会下发它）；
  3. Redis：`settings.redis_url` 非空（照 `app/services/rate_limit.py` 的 `if not redis_url`）；
  4. `sms_max_cost_micro_usd_my` 与 `sms_max_cost_micro_usd_sg` 都为大于 0 的整数；
  5. `sms_daily_count_limit`、`sms_daily_cost_limit_micro_usd`、`sms_phone_limit_per_minute`、`sms_phone_limit_per_hour`、`sms_phone_limit_per_day` 与 `sms_source_limit_per_hour` 都为大于 0 的整数。
  第 4、5 类的「整数」排除布尔值（`isinstance(value, int) and not isinstance(value, bool)`）。判定放在接口文件，服务层引用 `app/api/site_settings.py` 会循环导入（HANDOFF 0.65）。
- 两个接口的变化（路由类、no-store、`require_admin` 与不写日志都照旧；路径存在而方法不匹配的 405 不在 no-store 之列）：
  - `GET /api/admin/site-settings`：在 `payment_method`、`stripe_available`、`csrf_token` 之后加 `sms_verification_enabled`（照 `is_sms_verification_enabled`）与 `sms_available`（当次请求的 `sms_service_configured(request.app.state.settings)`）。仍只读、不写审计。
  - `PUT /api/admin/site-settings`：请求体模型改名 `SiteSettingsIn`，`payment_method` 照旧必填；新增可省略的 `sms_verification_enabled`，`strict=True` 下只接受 JSON 布尔值，字符串、数字、null 一律 422（沿用 `_body_errors`，不回显）；`extra="forbid"` 不变。省略与否看 `model_fields_set`，省略时传 None 给保存函数。检查顺序 413（8 KB）→ 415 → 401 → 403 `csrf_failed` → 422 请求体 → 支付方式为 stripe_test 而凭据不可用时 422 `{"detail":"stripe_not_configured"}` → `sms_verification_enabled` 为 true 而短信服务不可用时 422 `{"detail":"sms_not_configured"}`（当前已开启也一样）。两种拒绝都在锁定与写入之前，不写入任何一项、不写审计；字段为 false 或省略时不调用 `sms_service_configured`。成功回 200 与保存后的 `payment_method` 和 `sms_verification_enabled`（响应模型 `AdminSiteSettingsSavedOut`）。
- 保存：`save_payment_method` 改名扩展为 `save_site_settings(db, admin_account_id, method, sms_enabled, stripe_available, sms_available, now) -> (保存后的支付方式, 保存后的短信开关, 是否改动)`，拒绝的异常 `PaymentMethodRejected` 改名 `SiteSettingsRejected`（调用方只有该接口）。照原写法：先判两种拒绝（先支付方式再短信，不查库）；回滚此前的事务后以 `lock_site_setting_statement()` 锁住站点设置行（行不存在时照原写法在保存点里插入）；两项各自与锁住那一行的当前值比较——支付方式按 `get_payment_method` 的规则，短信按 `is_sms_verification_enabled` 的规则（`bool(列值)`，取自锁住的那一行，保存前后都不另发 SELECT；省略时不比较）；都相同时回滚、不写入、不写审计；否则只改有变化的项与更新时间，每项变化各经 `record_audit` 写一条审计后一并提交。模块说明里「短信验证开关暂不提供写入」「短信验证开关不动」随之改写。
- 审计：支付方式照旧 `admin_payment_method_changed`；短信为 `admin_sms_verification_changed`（对象类别 `site_setting`、对象 ID 为该行 ID、旧值与新值为 `on` 或 `off`，操作者为当前管理员）。两项同时变化时写两条，同一次提交，发生时间都等于该行的更新时间。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 第 4、5 类的数值在 `Settings` 里声明为 int，经环境变量读入时不会是布尔值；布尔值的排除只在绕过校验构造配置（如 `model_copy`）时起作用，按验收照写。
  - 第 3 类按 `rate_limit.py` 的写法只判断非空：只有空白的连接串算已配置（`rate_limit.py` 也把它当已配置，运行时连不上按停发处理）；格式不对的连接串同样不在保存时发现（DESIGN 1.15「检查只看配置，不在保存时连接服务商或 Redis」）。
  - 保存函数收到的 `sms_available` 在字段为 false 或省略时由接口直接给 True、不调用判定，使「保存『关闭』不检查」在代码里也不读短信配置；该值在这两种情况下不参与判断。
  - 请求体里的短信字段默认值 `False` 只是省略时的占位，接口以 `model_fields_set` 区分省略；选这个写法而不用 `bool | None`，是因为后者会接受显式的 null（验收要求 null 422）。
  - `PUT` 的返回不带 `sms_available`、`stripe_available` 与 `csrf_token`（验收只要求保存后的两项）；页面要最新的可用状态时再 GET。
- 现有测试的修改（只在必要处，各处在测试里写明原因）：`test_malformed_body_is_422_without_echo` 去掉不再是 422 的 `with-sms-toggle`（`sms-toggle-secret` 与 `only-sms-toggle` 仍为 422），说明改写；`test_get_returns_method_availability_and_csrf_token` 的整体比较与字段顺序在末尾补两个新字段，说明里「不返回短信验证开关」改写；`test_failed_saves_write_no_audit` 里带布尔短信字段的那次保存改为短信字段取字符串 `"false"`；把 PUT 成功的响应体比作只含 `payment_method` 的断言补上 `sms_verification_enabled`（新增常量 `SAVED_SIMULATED`、`SAVED_STRIPE_TEST`）；`make_settings` 改为接受任意类型的覆盖值，`redis_url` 移入可覆盖的默认值，现有调用得到的配置不变；`test_saving_does_not_touch_the_sms_toggle` 期望不变，说明的依据改为 HANDOFF 0.65（1）；`_audits` 加可选的操作名参数，默认仍是支付方式审计。
