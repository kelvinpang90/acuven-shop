# SHOP-TASK-091 支付页与结果页的会员接口

- [x] 按 `docs/DESIGN.md` 1.11（提交 `2d13250`）「订单与退款状态」（待支付订单可由下单者在支付页取消，会员凭登录会话）与「权限与资料保护」第 6 条（会员仅能访问自己认领或下单的订单；支付、取消等写操作另须 CSRF 令牌），以及 `docs/UX.md` 0.10 P06、P07（会员凭登录会话访问支付页与结果页；成功后会员看到本单获得积分；会员可从 P09 会员模式回到 P06 继续支付或取消），在 SHOP-TASK-090 之上新建 `app/api/member_pay.py`（`app/main.py` 挂上路由），提供 `POST /api/member/pay/order`、`POST /api/member/pay/attempts` 与 `POST /api/member/pay/cancel`；测试见 `tests/test_member_pay_api.py`。不做前端；未改 `app/api/pay.py`、`app/services/`、`app/api/member_auth.py`、`.platform/`、CI、部署配置与设计，未加表或迁移，未装依赖。设计闸门：DESIGN 1.11（提交 `2d13250`）与 HANDOFF 0.47（优惠券与积分）。拆分：接口层（4 个允许路径）。
- 接口：路由器 `prefix="/api/member/pay"`，用 SHOP-TASK-027 的 `_NoStoreRoute`，三个接口的处理函数与依赖产生的全部响应（含 401、403、404、409、413、415、422 与 `get_session` 的 503）都带 `Cache-Control: no-store`；路径存在但方法不匹配的 405 由框架在路由之外回答，不在此列。只凭会员会话（`app/api/member_auth.py` 的 `MemberDep`，401 `member_session_required`），不读订单访问 cookie；订单号只在请求体里，不进任何路径或查询参数。请求体读取（`_json_body`，8 KB 逐块）、`PaymentIn`/`CancelIn`、幂等键校验（`PaymentDep`）、`_body_errors`、`LanguageDep` 与 409 的 `_conflict` 都从 `app/api/pay.py` 引用，不复制。本模块不写日志。
- 授权：按请求里的订单号查订单，订单号不合法（`is_valid_order_number`）、订单不存在或 `member_id` 不等于该会员一律 404 `{"detail":"order_not_found"}`，不回显订单号。会员认领的游客订单与会员下单的订单都以 `member_id` 归属该会员，所以「自己认领或下单」只按 `member_id` 判断，不限创建时间。
- 查看 `POST /api/member/pay/order`：检查顺序为 413（8 KB，逐块）→ 415 → `require_member`（401）→ `lang`（同 `GET /api/pay/orders`：`en`、`zh`、`ms`，默认 `en`，不合法 422 不回显）→ 请求体只有 `order_number`（多出字段 422，不回显）→ 404。只读，不要求幂等键与 CSRF。订单待支付时先对它执行 `expire_overdue_orders`（逐张提交），再以 `pay_orders` 的视图返回这一张订单（`PayOrder` 的全部字段：含收货资料与 SHOP-TASK-090 加的 `coupon_discount_sen`、`points_redeemed`、`points_earned`）。
- 支付 `POST /api/member/pay/attempts` 与取消 `POST /api/member/pay/cancel`：请求体与 413 → 415 → 422（幂等键只有支付要，规则同下单接口）沿用游客接口；之后 `require_member`（401）→ `require_member_csrf`（403 `csrf_failed`）→ 查订单（404）；再以 `actor="member"` 调用 `submit_payment` 与 `cancel_order`。成功（支付新写 201、重放 200；取消 200）与 409（`idempotency_conflict`；`order_expired`、`order_not_payable`、`order_not_cancellable` 另带 `status`）的状态码、响应体与 `detail` 和游客接口相同。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 两个写接口的 422 先于会员会话检查（没有会话而请求体多出字段时 422），这是验收写的「沿用 `app/api/pay.py` 的对应接口（413 → 415 → 422）」；查看则按验收先 401 再 422。两者顺序因此不同。
  - 查看的 `lang` 在会话之后、请求体结构之前判断（`LanguageDep` 作为依赖排在 `MemberDep` 之后），与会员计价接口相同。
  - CSRF 在查订单之前：没有 CSRF 时，他人的订单号与自己的订单号都是 403，不因订单号而不同。
  - 查看只返回一张订单的 `PayOrder` 对象本身，不像游客的 `GET /api/pay/orders` 包一层 `orders` 并附 `csrf_token`；会员的 CSRF 令牌由 `GET /api/member/session` 给出。
  - 与游客接口相同，不另做限流，数据库出错时不另转 503（交给框架）；会员已注销后订单的 `member_id` 被清空，这类订单对任何会员都是 404。
- 留给之后的任务：前端会员模式（P06、P07 以会员身份显示与操作，含 `[result.points_earned]`，以及 P09 会员模式的 `[account.order_pay]` 跳转）留给之后的前端任务（规划块「已阻塞」里的「短信验证组件 V1 与结账会员路径」与会员中心 P13 那一项）；会员订单列表与订单详情接口不在本任务。
- 验证到什么程度：人工逐条对照验收标准、DESIGN 1.11 原句与 UX 0.10 P06、P07 自查，人工核对依赖的声明顺序（请求体依赖在会员依赖之前）与 `_NoStoreRoute` 对依赖错误的转换。`tests/test_member_pay_api.py` 用 `TestClient`（`https://testserver`）与 SQLite 内存库（StaticPool，每个连接打开外键检查，并断言已打开；写法照 `tests/test_demo_payment.py` 与 `tests/test_member_pw_api.py`），会员订单按模型写入，券与积分经 `reserve_coupon`、`reserve_points` 预占，来源批次经 `earn_points`；会员会话经 `issue_member_session` 签发，游客订单的访问 cookie 经 `issue_order_access` 签发；未加依赖。每条测试的文档字符串写明它守住的设计、UX 或验收条目。覆盖：会员查看自己的待支付订单（全部字段、收货资料、三个快照字段、no-store、不写库）、按语言取订单行与不合法语言 422；200 天前已支付的订单照常查看并给出 `points_earned`；认领的游客订单可查看与支付；超时的待支付订单查看时已为 `demo_cancelled`、取消方为超时、券与积分已释放、库存加回、事件为 system；查看、支付、取消其他会员与游客的订单、不存在或不合法的订单号都 404 且不改订单；支付成功写 member 事件、用券记录为 `used`、按快照发放积分、视图给出 `points_earned`；支付失败不核销不发放；取消写 member 事件、释放券与积分（可用余额恢复）、加回库存，重复取消不再释放；缺、错、重复或拿游客订单的 CSRF 令牌 403 且不改订单，CSRF 先于查订单；未登录、会话不合法或已退出 401；只带游客订单访问 cookie（连同其 CSRF）401，已登录会员同时带游客 cookie 访问该游客订单仍 404；重放、同键不同内容、已支付再付与取消、已取消再付、重复取消、超时后支付与取消，会员接口与游客接口的状态码与响应体逐一相同；超过 8 KB 413 先于一切、不是 JSON 415 先于会话、查看 401 先于 422、写接口 422 先于会话、多出字段与类型不符 422 不回显、支付缺或不合法的幂等键 422；OpenAPI 里该前缀只有三个 POST，订单号不在路径或查询参数里；200、201、401、403、404、409、413、415、422 都带 no-store；没有 `app.` 日志。未在真实浏览器或真 MySQL 上验证。这些测试与已有后端测试只由 PR 的必需 CI 检查 backend 执行，Worker 沙箱不跑 pytest。检查命令结果由 Worker 另行记录。
