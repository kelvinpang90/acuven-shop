- 判定顺序（`send_verification(db, settings, redis_client, provider, captcha, phone_e164, purpose, captcha_token, source, now) -> SendOutcome`），任一步不通过即停止：1 当次读取的开关（`site_settings.is_sms_verification_enabled`）关闭即 `sms_disabled`（不核验人机挑战、不调用服务商、不预占、不计限流、不写记录）；2 号码不属于短信白名单（`phone.is_sms_whitelisted`）即 `not_whitelisted`（不写记录）；3 Turnstile `failed` 即 `captcha_failed`（不写记录），`unavailable` 停发；4 Redis 限流，超限即 `rate_limited`（不写记录，不降级），客户端为 `None` 或抛 `RateLimitUnavailable` 停发；5 每日预算预占，`unknown_cost` 或 `over_budget` 停发；预占成功即提交；6 调用服务商。
- 结果与记录（写记录与结算或释放在第二个事务里一起提交）：
  - `accepted`：没有该请求 ID 的记录时写 `sent` 记录（带请求 ID）并结算，返回 `sent`。
  - 沿用请求 ID：已有记录属于同一号码且为 `sent` 时不新增记录，以条件更新（仅当仍为 `sent`）把它改为本次结果的状态（`accepted` 为 `sent`，带请求 ID 的 `undeliverable` 为 `undeliverable`）、本次用途与当前更新时间，照样结算。已有记录为 `approved`、`rejected`、`undeliverable`（含条件更新时已被改掉的）或属于另一个号码时原记录不改，写 `suspended`、释放本次预占，返回 `suspended`（Kelvin 2026-10-09）。
  - `undeliverable`：写 `undeliverable` 记录；有请求 ID 时带上并结算，没有时释放；返回 `undeliverable`。
  - 停发（Turnstile 服务不可用、Redis 为 `None` 或不可用、预算拒绝、服务商 `unavailable`）：写不带请求 ID 的 `suspended` 记录，已预占的释放，返回 `suspended`。未取得预占的停发不调用释放。
  - 记录的用途为调用方给出的用途、创建与更新时间为 `now`，与 `ordering.py` 现有的降级判定（最近 30 分钟、用途 `checkout`、状态 `undeliverable` 或 `suspended`）衔接。
  - 预占前或预占时 MySQL 出错、服务商抛出异常、第二个事务失败（含并发插入撞上请求 ID 唯一约束）时异常交给调用方，不重读、不重试；已提交的预占保留为 `reserved`（保守计入每日上限），这次没有记录。
  - 交给调用方的异常：数据库异常（`SQLAlchemyError`，如撞唯一约束时的 `IntegrityError`，其消息带 INSERT 参数中的完整号码）与服务商调用抛出的任何异常，在两个函数里都换成 `SmsVerificationError`（`RuntimeError` 子类），消息固定为 `sms verification storage failed` 或 `sms provider call failed`，在 except 块之外抛出、不挂原异常（`__cause__` 与 `__context__` 都为空）；会话由调用方回滚。用途与号码格式的 `ValueError`、`InvalidPhoneNumber` 与每日预算的 `SmsBudgetError` 消息本就固定，原样抛出。
- 限流（Kelvin 2026-10-08 标准档）：配置项 `sms_phone_limit_per_minute`（默认 1）、`sms_phone_limit_per_hour`（5）、`sms_phone_limit_per_day`（10）、`sms_source_limit_per_hour`（10），变量名与 `.env.example` 已登记的一致；每个国家呼叫码 24 小时的上限取 `sms_daily_count_limit`（默认 200）。桶名 `sms_phone_minute`、`sms_phone_hour`、`sms_phone_day`、`sms_source_hour`、`sms_country_day`，号码、来源与国家呼叫码都只以 `rate_limit_key` 的摘要进 Redis。按上列顺序逐桶 `hit`，第一个超限的桶即 `rate_limited`，其后的桶不再计数，已计入的桶不回退。
- 核验（`verify_code(db, provider, phone_e164, purpose, code, now) -> VerifyResult(status, attempt_id)`）：当次从数据库读取的开关关闭即 `sms_disabled`（不调用服务商）；验证码不是 4 到 10 位 ASCII 数字即 `wrong_code`（不调用服务商）；找该号码与用途 `now - 10 分钟 <= created_at <= now`、状态 `sent` 的最新记录（按创建时间、再按 ID 倒序），没有即 `no_pending`；按其请求 ID 调用服务商：`approved` 以条件更新（仅当仍为 `sent` 且用途仍是读取时的用途）改为 `approved` 并返回记录 ID，`expired` 以同样的条件更新改为 `rejected` 返回 `expired`，两者更新不到即 `no_pending`；`wrong_code` 与 `unavailable` 不改记录。只 flush、不提交。
- 不泄露：本模块不写日志；返回值只有类别与记录 ID；异常消息固定，不含手机号、验证码、令牌与来源。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 两个函数都先读开关：关闭即返回 `sms_disabled`（用途不合法也一样，不抛异常）；开关开启而用途不在 `VERIFICATION_PURPOSES` 里时抛 `ValueError`（编程错误，在白名单、人机挑战与验证码格式之前，不调用任何服务、不写记录）；号码不是规范化 E.164 时由 `is_sms_whitelisted` 抛 `InvalidPhoneNumber`。
  - 服务商返回 `accepted` 却没有请求 ID 时按 `unavailable` 停发（记录不能没有请求 ID 而为 `sent`）。SHOP-TASK-067 的适配器的 `undeliverable` 从不带请求 ID；带请求 ID 的分支按验收实现，只由测试替身覆盖。
  - 国家呼叫码以 `normalize_phone(号码, "MY").country_code` 取得（号码以加号开头，默认地区不起作用）。
  - 返回 `sms_disabled`、`not_whitelisted`、`captcha_failed`、`rate_limited` 时只读过开关，不提交也不回滚，事务由调用方结束；预占前或预占时出错、第二个事务失败时本模块也不回滚，由调用方回滚。
  - 不另记验证码尝试次数：本地挡掉的格式不对的验证码（SHOP-TASK-067 记录段提到）不计入，尝试次数用尽由 Twilio Verify 判定（归为 `expired`）。如需本地计数须另行决定。
- 留给之后的任务：发送短信验证码接口与把各结果转成回答（SHOP-TASK-070）；登录、注册、密码重设与认领（之后登记的会员任务，照本模块的 `verify_code` 调用并与之后的步骤一起提交）；验证记录 30 天后删除（Kelvin 2026-10-08）；超过每日总量或费用阈值时的运营告警邮件。

## 登记时的验收标准（原文）
