# SHOP-TASK-097 超时取消逐张订单独立提交

- [x] 按 `docs/DESIGN.md` 1.11（提交 `2d13250`）「计价、优惠、积分与库存」第 6 条（15 分钟未支付自动取消并释放；每天按马来西亚时间重建当日可用库存为初始库存减去仍有效的预留）与「失败、并发与重试」第 1、6 条（库存、券与积分预占在同一事务；定时任务可重复运行、只生效一次），让定时任务与每日库存重置里的超时取消逐张订单真实提交：`app/jobs.py`、`app/services/stock_reset.py`；测试见 `tests/test_jobs.py`、`tests/test_stock_reset.py`。只改事务边界：超时取消本身（`app/services/payment.py` 的 `expire_overdue_orders`）与库存重置的计算不变；未改模型、迁移、其他任务、部署配置与 docker-compose 文件、`.platform/`、CI 或设计，未加表，未装依赖。设计闸门：DESIGN 1.11（提交 `2d13250`），订单状态迁移的执行方式。拆分：定时任务（5 个允许路径）。
- 起因：SHOP-TASK-090 让取消先锁会员行再加回库存。原来运行器的超时取消任务（SHOP-TASK-031）与库存重置里的超时取消（SHOP-TASK-032）都在一个外层事务里以保存点连续取消多张订单，前一张订单的库存行锁持有到外层提交；再去锁下一张订单的会员行时，会与会员下单（持会员锁、等库存）成环（登记时的预审与 Codex 审查指出，2026-10-11）。游客下单（按库存顺序加锁）与这两处之间本来也有同类情形，随之消除。
- 运行器（`app/jobs.py`）：`cancel_expired_job` 返回的 `Job` 设 `own_transactions=True`，`run_job` 给它不在事务中的新会话，`expire_overdue_orders` 每张订单的 commit（未命中时 rollback）即真实提交与回滚，没有到期订单时只读的事务随会话关闭回滚。任务名 `cancel_expired_orders`、每轮上限 `CANCEL_BATCH_LIMIT` = 100、在 `default_jobs()` 里的位置（第一项）与手动命令 `cancel-expired` 不变。`run_job` 对非 `own_transactions` 任务的保存点做法不变（默认列表里已没有这样的任务）。模块说明的每轮步骤与事务说明、`run_job` 与 `cancel_expired_job` 的说明随之改写。
- 每日库存重置（`app/services/stock_reset.py` 的 `reset_daily_stock`）：检查到该日期尚未完成并结束检查的事务之后、开始认领事务之前，直接在该会话上执行一次 `expire_overdue_orders`（不限张数，逐张真实提交），返回后不论取消了几张都先 `rollback`（没有到期订单时它只做了 SELECT、留下只读事务；MySQL 上认领事务要在新事务开始时设 READ COMMITTED）；然后照旧 `_begin`、认领、按规格 ID 加锁统计与写入。该日期已完成时不执行超时取消。删去以保存点在认领事务里执行超时取消的 `_expire_overdue`。统计规则不变：仍把所有 `awaiting_demo_payment` 订单的件数算作有效预留，所以在超时取消与认领之间新到期的订单照旧计入、不影响结果，下一轮的超时取消任务再取消并加回。模块说明的步骤（新的第 2 步）与事务说明、`_begin` 的说明随之改写。
- 失败时的行为变化：
  - 超时取消任务：某张订单取消时抛异常，只有这一张回滚；之前已取消的订单保留（各自已提交），本轮记 `job cancel_expired_orders failed: <异常类名>`、该任务按失败计时，下一轮继续（它们已不是待支付，不会重复取消）。原来整次运行一起回滚。
  - 库存重置：超时取消这一段抛异常时回滚、在独立事务里记 `failed`（只记异常类名）并把原异常交给调用方，已逐张提交的取消保留，不认领、不写库存与明细；认领之后（统计、写入）失败时认领事务回滚并记 `failed`，已提交的超时取消保留。原来重置失败时这些取消一起回滚。
  - 收到停止信号强制退出时，超时取消任务未提交的只有正在处理的那一张，已提交的取消保留；每张订单的取消、加回库存与事件仍在同一个事务里，不会留下半张。
- 偏离与取舍，请审阅（未改设计，未发现须停下的设计问题）：
  - 库存重置的超时取消抛异常时记为 `failed`，与认领之后失败相同（按验收）；这时该日期还没有认领，`_record_failure` 照旧先条件 UPDATE、未命中再插入，所以检查之后另一个执行者已成功时不覆盖 `succeeded`。
  - 超时取消与认领之间加了一次 `rollback`，即使取消了订单（此时最后一张已提交或回滚、会话不在事务中，回滚不做任何事）也执行，按验收的写法不区分。
  - `tests/test_jobs.py` 与 `tests/test_stock_reset.py` 只为本任务修改与新增：`test_failure_is_recorded_and_retry_succeeds_once` 改为断言重置失败时超时取消已生效（状态、加回的库存与 system 事件）、库存与明细回滚，重试后每张只取消一次；`test_overdue_orders_are_cancelled_before_counting` 加上开始认领事务时订单已取消且会话不在事务中；两个测试文件的模块说明随之补充。自定义的非 `own_transactions` 任务在运行器里的失败回滚用例（`test_failure_after_committed_cancellations_rolls_back_the_whole_run`）不改。没有删减或放宽其他原有用例。
- 留给之后的任务：SHOP-TASK-090 在 `expire_overdue_orders` 的取消路径里接入券与积分的释放（先锁会员行）；本任务只保证调用它的两处不再跨订单持锁。
- 验证到什么程度：人工逐条对照验收标准与设计原句自查，人工核对 `expire_overdue_orders` 在有到期订单时以最后一张的 commit 或 rollback 结束事务、没有到期订单时留下只读事务，以及两处调用方在它返回后的事务状态。新增与修改的测试用 SQLite 内存库（引擎设置不变：由引擎发 BEGIN，内存库只有一条共享连接），每条测试的文档字符串写明它守住的设计原句或本任务的约定，覆盖：运行器与 `cancel-expired` 以 `own_transactions` 执行超时取消（会话不在事务中，上限仍为 `CANCEL_BATCH_LIMIT`）；同一轮里每张订单取消后、取消下一张之前另开会话即可读到已取消（若有未提交的外层事务，另开会话的 BEGIN 会出错），重复运行每张只取消一次、库存只加回一次；超时取消任务第二张取消时抛异常，第一张已取消并保留、第二张未变、本轮记失败且日志只含任务名与异常类名，下一轮取消第二张、每张只一个 system 事件；库存重置失败时超时取消已生效、库存与明细回滚，重试成功后只有一份明细；超时取消发生在开始认领事务之前；该日期已完成时不执行超时取消；没有到期订单时开始认领事务之前会话不在事务中；超时取消这一段抛异常（以替身让第二张的取消抛锁等待超时）时记为 `failed`（只存异常类名）、原异常交给调用方、第一张的取消保留、不写明细，再次执行时取消第二张并完成重置、尝试次数 2。这些测试只由 PR 的必需 CI 检查 backend 执行，Worker 沙箱不跑 pytest。行锁的释放时机与成环是否消除只能在真 MySQL 上体现，SQLite 测试只验证提交边界；未在真 MySQL 上做并发演练（会员下单与超时取消、游客下单与库存重置并发）。检查命令结果由 Worker 另行记录。
