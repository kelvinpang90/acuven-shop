## 边界与原则

- 金额以 MYR 的仙（sen）为整数单位运算；积分数量一律称「积分」，不把仙与积分混称。其他货币只按管理员配置的固定演示汇率显示参考数，不参与结算。页面、订单与后台明确标为演示；无真实收款、退款、寄送或税费。本站页面不提供银行卡输入；支付方式为「Stripe 测试」时，付款页由 Stripe 托管、只用测试密钥，提示访客只用测试卡号（见「Stripe 测试环境支付」）。
- 公开访客可填真实或虚构收货资料；唯一例外是短信验证开关开启时，未登录访客的结账手机号属于短信白名单国家时，须真实可收短信（见「权限与资料保护」）。仅收集姓名、电话、国家、地区、地址及邮编等完成演示所需字段，不要求邮箱或证件。收货资料原文与订单、商品和状态历史一并长期保存，不删除、不匿名化（Kelvin 2026-09-29 决定，风险见「资料保留」）。会员手机号保留至主动注销。
- 初期短信验证只开放马来西亚和新加坡，且以服务商实际送达能力为准；这两国手机号结账下单前须短信验证并成为会员。白名单外号码不验证，继续游客下单；白名单内号码无法送达或短信服务停发时不声称注册成功，允许改为游客下单。真实短信会产生外部费用。
- **短信验证开关**（Kelvin 2026-10-01 决定）：管理员在后台「站点设置」开关全站短信，默认关闭。关闭时全站不发任何短信：未登录访客的任何号码（含马新号码）都不验证、以游客下单；注册、短信登录与密码重设暂停；会员注销改以密码或已登录会话确认（见「权限与资料保护」）。开启时按上一条及下文执行。本文其余各处所说的短信验证、白名单判定与短信降级，均只在开关开启时适用。下单、发送短信、提交验证码与确认注销时，服务端都按当时读取的开关值判定：开关在流程途中被关闭后，提交的验证码不再核验，不登录、不注册、不重设密码，也不能以短信完成注销确认，前台改显示暂停提示；关闭前已建立的会员会话不受影响。开关在流程途中被开启后，已进入游客表单的马新号码下单被拒，须回到结账第一步验证。
- 「访客国家货币」按收货国家决定，不按 IP；该国无演示汇率时只显示 MYR，不猜测或临时请求实时汇率。

## 数据模型

| 对象 | 字段与关键约束 |
| --- | --- |
| `Product` / `Variant` | 商品、分类、三语文案、图片引用、规格属性、MYR 单价、启用状态；商品级的每单限购件数（`Product` 上非空的整数，1–99，默认 10，不按规格分别设置）；每个规格有 SKU、管理员设定的每日初始库存及当日可用库存。价格与数量不得为负；文案缺少当前语言时回退英文，再缺失则商品不发布。 |
| `ShippingRate` / `DemoFxRate` | 国家运费、马来西亚州属运费、“其他国家”兜底运费；参考币种固定汇率及版本。下单存计算规则版本与金额快照。 |
| `SiteSetting` | 站点级运营开关：短信验证开关（布尔，默认关闭）与支付方式（模拟 / Stripe 测试，默认模拟）。每次判定都从数据库读取当前值、不缓存，修改对之后的请求立即生效；后台修改写入 `AuditEvent`（操作者、时间、新旧值）。 |
| `Coupon` / `CouponUse` | 固定金额或百分比、有效期、最低商品消费、总使用上限、每会员使用上限、启停状态；使用记录与订单关联。 |
| `Member` / `VerificationAttempt` | E.164 格式手机号、可为空的密码哈希（短信验证自动注册时尚未设置）、账号状态；Twilio Verify 托管验证码，只存提供方请求 ID、结果与限流元数据，不存验证码。 |
| `Cart` | 浏览器中的商品规格与数量；不信任浏览器价格，结账时服务端重算。 |
| `Order` / `OrderItem` | 不可猜测的订单号、可选会员 ID、状态、MYR 价格/优惠/积分/运费/应付快照、幂等键、创建与支付时间；商品名称、规格、数量、单价，以及逐件优惠、积分、现金实付、获得积分的分摊快照。订单摘要不依赖收货资料记录存在。 |
| `OrderRecipient` | 收货姓名、规范化 E.164 电话、地址、邮编等原文，引用所属订单并为电话建立查询索引；长期保存，不设到期删除或匿名化任务；改变此规则须另行批准。收货资料不做应用层加密。 |
| `PaymentAttempt` / `OrderEvent` | 模拟支付选择与结果、状态变更、操作者类别、时间、幂等键；事件不写收货资料原文。 |
| `StripeCheckout` / `StripeEvent` / `StripeRefund` | Stripe 测试环境的对账记录，不存客户资料。`StripeCheckout`：所属订单、本站创建幂等键（唯一）、Checkout 会话 ID（可空，唯一）、PaymentIntent ID（可空，唯一）、金额（仙）、币种、状态（creating / open / complete / expired）与付款状态、实际付款方式类型（可空）、付款页地址、创建参数快照（金额、语言、返回地址、Stripe 到期时间）、创建与完成时间；同一订单至多一条不是 expired 的记录，由一个只在 creating、open、complete 时等于订单 ID 的列上的唯一索引保证。`StripeEvent`：Stripe 事件 ID（唯一）、类型、处理结果与时间，与事件引起的改动同一事务提交，不存原文。`StripeRefund`（每条是一次退款尝试）：所属 PaymentIntent、来源（退款申请或迟到付款的会话）及其 ID、Stripe 退款 ID（可空，唯一）、金额（仙）、状态（pending / succeeded / failed，Stripe 的 requires_action 记为 pending、canceled 记为 failed）、调用次数、最后的错误类别、创建与成功时间、上次复查时间；本站 ID 即幂等键并写进 Stripe 退款元数据；同一来源至多一条不是 failed 的尝试，由一个只在非 failed 时等于来源的列上的唯一索引保证。 |
| `RefundRequest` / `RefundLine` | 申请状态、每个商品规格的申请数量、按原订单快照计算的可退商品金额、审核人及理由；每件商品累计批准退款数量不可超过购买数量。 |
| `PointLedger` | 获得、抵扣、到期、退款追回、待抵扣积分的不可覆盖流水；每笔关联订单或退款，余额不得小于零。 |
| `AdminAccount` / `AuditEvent` | 单一管理员、密码哈希、会话及后台操作记录；图片只存引用与必要元数据。 |

## 计价、优惠、积分与库存

1. 服务端以订单规格价格快照计算商品小计；优惠券先抵商品额，积分再抵剩余商品额，二者均不抵运费，最终应付不得低于运费。优惠券仅会员可用，使用额度在下单时预占，取消或支付超时释放。
2. **逐件分摊**：先将商品按稳定的订单行序与件序展开。百分比券对整单商品小计计算一次，以十进制定点数按“四舍五入，恰好半仙进一仙”得到整仙折扣；固定金额券取券额与商品小计较小者。将整单券折扣按每件原价占商品小计的比例分摊；再将积分抵扣按每件券后金额占整单券后金额的比例分摊。每次分摊先向下取整到仙，余下的仙依小数余数从大到小补 1 仙，平手按订单行序、件序。分母为零时抵扣为零。每件现金实付 = 原价 − 分摊券额 − 分摊积分额；运费另计。整单及逐件分摊快照不可因后来改价而重算。
3. **获得积分**：模拟支付成功后，先对整单商品现金实付合计每满 100 仙（RM1）给 1 积分，再按逐件现金实付比例用同一“最大余数、稳定序”算法分摊获得积分；不按行分别取整。100 积分抵 RM1。积分批次在取得后 12 个月到期，先到期先使用；结账抵扣时预占，失败或取消时释放。游客不积累积分，提示注册；认领过去游客订单不追发积分。
4. **分摊算例**：A 商品 2 件、各 RM10；B 商品 1 件、RM5。整单 10% 券减 RM2.50，分摊到 A 每件 RM1、B RM0.50；使用 300 积分抵 RM3，分摊到 A 每件 RM1.20、B RM0.60。三件现金实付依次 RM7.80、RM7.80、RM3.90，共 RM19.50，整单获得 19 积分，按稳定序分给 8、7、4。仅退第一件 A 且原抵扣积分尚未到期时，模拟退现金 RM7.80，返还原抵扣的 120 积分，并追回该件获得的 8 积分；券不退、示例运费不退。这里的“每件实际支付商品额”**只指现金实付，不含积分抵扣**。
5. 退款批准时按原逐件快照返还未过期的抵扣积分并追回获得积分；积分余额不足时扣至 0，缺口记待抵扣。原抵扣积分批次若已经过期，不返还已过期积分。任何次数的部分退款满足：累计模拟退现金 ≤ 该单商品现金实付合计；累计返还抵扣积分 ≤ 该单实际抵扣积分；累计追回获得积分 ≤ 该单实际获得积分。
6. 管理员设置每个 SKU 的每日初始库存。下单事务预留当日可用库存，支付成功消耗预留，失败重试期间保持预留，15 分钟未支付自动取消并释放（有 Stripe 记录的订单，取消时机按「Stripe 测试环境支付」第 5 条）。每天按马来西亚时间重建当日可用库存为“初始库存减去仍有效的预留”，记录重置事件；历史订单不变。模拟退款不回补库存，避免跨日重复增加。管理员当天修改初始库存仅从次日重置生效；当天可用库存不回写，需单独执行当日库存调整。
7. 商品、优惠、运费、汇率或积分规则的后台修改只影响新订单，已有订单及退款按快照计算。图片上传限制文件类型、大小并隔离存储，不能当可执行文件使用。
8. **每单限购**：同一商品所有 SKU 在一张购物车或订单中的件数合计不得超过该商品的每单限购件数；购物车最多 20 行（每行一个 SKU，同一 SKU 不重复），每行件数为 1–99 的整数。计价接口不因超出限购拒绝整个请求，而把该商品的各行标为超出限购并返回限购件数，标注优先级为不可购买、超出限购、库存不足；存在任何非正常行时不可下单。下单时服务端重新校验，超出限购即拒绝整单，不部分下单。限购与库存各自独立生效。修改限购件数按第 7 条只影响之后的计价与下单，不改已有订单与退款。

## 订单与退款状态

- 下单：`awaiting_demo_payment`；模拟支付失败仍停在此状态并记录失败尝试；成功进入 `demo_paid`。支付方式为「Stripe 测试」时，确认、取消与超时另按「Stripe 测试环境支付」第 4、5 条，状态本身不变。
- 管理员依次推进 `demo_paid` → `demo_packed` → `demo_shipped`；访客在查单页、会员在「我的订单」确认收货后进入 `demo_completed`。无真实物流单。若访客不操作，模拟发货满 7 天自动确认收货。自动完成只改演示状态，不影响 30 天退款期。
- 待支付订单可由下单者在支付页取消（游客凭该单短期凭据，会员凭登录会话），或超时为 `demo_cancelled`，释放库存、券及积分预占；已模拟支付订单不走取消，走退款流程。
- 支付成功后 30 天内可申请退款，包含已发货和已完成订单。退款与履约状态分开存储；`requested` → 管理员 `approved` 或 `rejected`。重复申请同一可退数量被拒绝；部分退款后余量仍可再次申请，总批准数量不超过购买数量。访客在查单页、会员在「我的订单」提交申请，只选商品与数量，金额按原单逐件现金实付快照计算，示例运费始终不退；系统显示累计已退及剩余可退金额。所有购买件数均已批准退款时，冻结后续打包/发货/确认收货的推进，保留退款前履约状态。
- 批准模拟退款时，按原计价分摊回退未过期的已抵扣积分，并追回该商品产生的积分。积分余额不足时扣至 0，剩余记待抵扣积分，以后获得积分先偿还；不出现负余额。已使用的券不恢复使用次数，避免重复领取优惠。所有退款均明确写“模拟”，无真实资金流；经 Stripe 测试付款的订单另在 Stripe 测试环境退款（「Stripe 测试环境支付」第 8 条），同样不涉及真实资金。
- 所有状态迁移校验当前状态、操作者与数量；事务内写订单、流水和事件。已批准的退款不可再次批准，已完成的履约状态不可倒退。

## 失败、并发与重试

- 下单、模拟支付、确认收货及退款申请/审核均使用幂等键和数据库唯一约束。相同键相同请求返回原结果；同键不同内容报冲突。库存预占、券/积分预占及订单创建在同一事务，失败全部回滚。
- 网络中断时先查询原订单或申请状态，再允许重试；不以页面重试次数推断操作成功。短信发送失败不创建已验证账号，提示游客继续体验；结账时白名单号码的短信无法送达或短信服务停发，允许改为游客下单，但验证码错误或超过尝试次数不降级为游客。
- 短信验证开关关闭时，所有短信发送请求在人机挑战核验、调用服务商与预占预算之前即被拒绝，不写验证记录，不计入限流与每日预算。这与「停发」不同：停发指开关开启时因每日预算、服务不可用或 Redis / MySQL 不可用而停止发送，按上一条的降级规则处理。
- 使用 Twilio Verify，由提供方负责验证码生命周期及防欺诈；系统只存验证请求与结果，不存验证码。发送前采用托管人机挑战，并在后端核验令牌。按规范化手机号、来源、国家及全站限流，超过每日总量或费用阈值停发并向运营告警邮件报告。短时限流计数存共享 `infra_redis` 为本项目分配的独立库编号，多 API 进程共用；Redis 数据丢失后这些计数清零可接受。**短信每日总量及费用预算另在本项目 MySQL 库以按日原子计数和预算记录兜底**：发送前按目的地预占保守的单次最高费用，未知费用时停发；结算后更新记录，防 Redis 重置后超过日上限。Redis 或 MySQL 不可用时短信停发。查单和管理员登录等依赖 Redis 限流的敏感接口也拒绝请求，商品浏览继续可用。不得把验证码、短信凭据或完整手机号写进日志。短信服务覆盖不足时展示明确错误。
- **初期短信国家（Kelvin 已确定）**：目的地白名单仅含马来西亚和新加坡；两国均须先验证服务商覆盖及运营权限，未通过验证的号码明确提示暂不可注册。结账验证、短信登录、注册与密码重设共用同一白名单、人机挑战、限流和每日预算。其他国家仍可游客下单；以后扩展白名单须另行变更设计并批准。
- 每日库存重置、积分过期均可重复运行，使用操作标识保证只生效一次；失败有告警与人工补跑办法。

## Stripe 测试环境支付

1. **只接测试环境**：只接 Stripe 测试环境（sandbox），不接正式环境。服务端只接受 `sk_test_` 或 `rk_test_` 开头的密钥，其他前缀（含 `sk_live_`、`rk_live_`）一律不启用 Stripe 支付并向运营告警邮件报告；webhook 事件、会话或付款的 `livemode` 为真即拒绝。按 Stripe 文档，测试环境不移动真实资金，访客应只用 Stripe 公布的测试卡号与（实测可用的）FPX、GrabPay 测试授权页；本站不以「Stripe 一定拒绝真实卡」作为保证，跳转前明确提示只用测试卡号、不要输入真实卡号与个人资料。改接正式环境即真实收款，须另行修改需求与设计并重新批准。
2. **支付方式开关**：`SiteSetting` 的支付方式取「模拟」（默认）或「Stripe 测试」，与短信验证开关一样每次从数据库读取、修改写审计；Stripe 密钥或 webhook 签名密钥未配置时不能切到「Stripe 测试」。服务端在访客发起支付时按当时的值判定。同一订单的两条支付途径互斥：订单只要有一条不是 expired 的 Stripe 记录（creating、open 或 complete），不论开关当前取值，都不接受模拟支付、不另建会话，支付页先按第 4 条向 Stripe 查询并确认，再只继续该会话；已经发起的会话，其确认、作废与退款不受之后切换的影响。现有的模拟支付提交、本人取消、查看触发的超时取消与定时任务都要改为在锁住订单的同一事务里先查该单的 Stripe 记录，按本条与第 5 条处理，实现任务须把这些现有入口一并列入。为「模拟」且没有 Stripe 记录（或只有 expired 记录）时，现有模拟支付流程不变。订单应付低于 Stripe 对 MYR 的最低收款额（配置项，默认 200 仙，以 Stripe 文档与账户结算币种为准）时，即使为「Stripe 测试」也走模拟支付。
3. **创建会话**：访客在支付页按现有授权（游客短期凭据或会员登录会话）与 CSRF 校验后发起。服务端先在加锁读订单的同一事务里写一条 `creating` 状态的 `StripeCheckout`：生成本站的创建幂等键，并把这次创建的全部参数（金额、语言、返回地址、Stripe 到期时间等）存为快照，提交；再以该键与快照调用 Stripe 创建 Checkout 会话（幂等键同时写进会话元数据），成功后锁住该记录写回会话 ID 与付款页地址：只在记录仍为 creating 时改为 `open`；若 webhook 已先把它记为 complete（或对账已记为 expired），只补齐缺失的会话 ID 与地址，不改状态与付款结果。调用结果未知（超时、断线）时，记录保持 `creating`，之后的发起或定时任务以同一幂等键与同一快照重试，取得同一个会话；快照里的 Stripe 到期时间过后，以同一幂等键再请求一次来对账（离创建远不到 Stripe 保留幂等键的 24 小时）：Stripe 回放原会话，说明当时已建成，记下会话后按它的实际状态处理（已付款按第 4 条确认，已过期才算 expired）；Stripe 以参数不合格（到期时间已过）拒绝，按 Stripe 幂等规则说明原请求没有建成会话，记为 expired；Stripe 不可用或答复冲突则留到下一轮，24 小时内仍无法确定就不再自动处理、告警由人工核对，订单在此期间不取消、库存继续预留。这一回放行为实现前先在测试环境核验，与本条不符时先改设计。万一有本站没记下会话 ID 的会话被付款，其 webhook 按元数据里的创建幂等键与订单 ID 对上这条记录，照第 4、6 条处理。同一订单至多一条不是 expired 的记录，由数据库唯一约束保证（记录上一个只在 creating、open、complete 时等于订单 ID、expired 时为空的列，对它建唯一索引）；已有 open 就直接返回它的付款地址。会话为 payment 模式，币种 MYR，金额等于订单应付快照，只有一个行项目，名称为三语文案里的「演示订单」，不含商品名、订单号或收货资料；`client_reference_id` 放本站订单的内部 ID；会话元数据放订单内部 ID（关联订单）与创建幂等键（遗失会话 ID 时由 webhook 找回 creating 记录），不放其他内容。付款方式限定为即时确认的方式：卡（含 Apple Pay、Google Pay）、Link、FPX、GrabPay，不启用延迟到账类方式；这些方式在这套会话配置下能否显示、测试授权的成功与失败如何呈现，实现前在测试环境逐一核验并记录，某种方式不可用时先修订本稿。预填配置的固定演示邮箱；不收集电话与送货地址，账单地址只在付款方式需要时由 Stripe 收集。语言按当前站点语言传给 Stripe，Stripe 不支持的语言交由 Stripe 自动判断。成功与取消的返回地址由配置的公开站点地址拼出，不取请求头里的主机；地址不带订单号、会话 ID 或任何凭据。会话的 Stripe 到期时间取订单支付到期时间与 Stripe 允许的最短时长（创建后 30 分钟）中较晚者。服务端只把 Stripe 返回的付款页地址交给前台跳转。从 Stripe 返回是顶层 GET 跳转，SameSite=Lax 的短期凭据与会员会话照常带上；游客短期凭据若已过期，访客凭订单号与电话查单。
4. **确认付款**：订单只在服务端确认 Stripe 付款成功后才进入 `demo_paid`，返回地址本身不作依据。确认有两个来源，走同一个幂等处理：签名校验通过的 webhook 事件 `checkout.session.completed`（`payment_status` 为 `paid`）或 `checkout.session.async_payment_succeeded`；访客从 Stripe 返回后前台调用本站接口，服务端按授权找到该单的会话向 Stripe 查询一次。确认时核对会话属于该订单、处于测试环境、币种为 MYR、金额等于订单应付快照；全部相符且订单仍为 `awaiting_demo_payment` 时，按模拟支付成功的同一事务进入 `demo_paid`（消耗库存预留、核销用券记录、按快照发放获得积分），并记下 PaymentIntent ID，以及从该 PaymentIntent 实际成功的那笔 Charge 读取的付款方式类型（`payment_method_details.type`，如 card、fpx、grabpay）；读不到时留空，不用会话的可用方式列表代替，由定时任务之后向 Stripe 重查补齐（只补这一字段，不再执行付款成功的状态迁移）。字段取法实现前在测试环境核验。订单的支付时间仍是本站确认时写入的时间，访客 30 天退款申请期限照旧以它起算；确认晚于 Stripe 付款时期限相应顺延，接受这一偏差。**确认不看订单的 15 分钟支付到期时间**，只看订单是否仍待支付：订单在会话结束之前不会被超时取消（第 5 条），所以访客在会话内完成的付款，即使确认晚于 15 分钟也照常确认，不当作迟到款。同一会话或同一 PaymentIntent 的重复确认（订单已由它付款）直接返回原结果，不退款、不重复发放。尚未确认时结果页显示「确认中」并稍后重查。卡被拒、FPX 或 GrabPay 授权失败由访客在 Stripe 页重试，不产生新订单。
5. **取消与超时**：有 Stripe 记录的订单，取消一律先处理会话，所有取消入口（本人取消、支付页与结果页查看时触发的超时取消、定时任务）用同一规则；查看入口只对没有 Stripe 记录（或只有 expired 记录）的订单执行超时取消，其余留给定时任务。会话为 creating 时先按第 3 条取得会话或对账，只有对账确认没有建成会话（记为 expired）才取消。会话为 open 时请求 Stripe 作废：作废成功或会话已过期才按现有规则取消；Stripe 答复会话已完成，按会话的付款状态处理。会话 complete 且已付款，按第 4 条确认、不取消；complete 而付款未定（按第 3 条的付款方式不应出现，出现时按此处理），订单继续待支付、库存继续预留，等 `checkout.session.async_payment_succeeded` 按第 4 条确认，或 `checkout.session.async_payment_failed` 后按现有规则取消；定时任务也定期查询该会话的付款状态，以 Stripe 给出的成功或失败为准，不因时间取消。会话完成 24 小时后仍无结果就告警，由运营者在 Stripe 后台跟进，订单照旧等待。Stripe 不可用时本人取消提示稍后再试，定时任务跳过该单留到下一轮；订单保持待支付、库存继续预留，恢复后按会话的实际状态处理，不以本地时钟过了会话到期时间代替 Stripe 的状态确认。24 小时仍无法查询就告警由人工核对，订单不自动取消。
6. **迟到与不符的付款**：确认时订单已不是待支付且不是由这个会话付款（已取消，或已由另一途径付款），或金额、币种不符，订单状态不变，服务端对这笔付款在 Stripe 测试环境全额退款，记为来源为该会话的 `StripeRefund` 尝试，并向运营告警邮件报告。
7. **webhook**：端点为 `POST /api/stripe/webhook`，用原始请求体与 webhook 签名密钥校验 `Stripe-Signature`（含时间容差），不通过回 400、不处理。事件 ID 的去重记录与它引起的订单、积分或退款改动在同一个数据库事务里提交：已提交过的事件直接回 200；处理失败整个事务回滚、回 5xx，由 Stripe 重发。业务动作另按对象去重（第 4 条按会话与 PaymentIntent，第 8 条按退款记录），不同事件指向同一动作时只生效一次。只处理第 4、5 条的 Checkout 事件与 Stripe 退款状态事件，其他类型回 200 不处理。不需要会话与 CSRF；不存、不记录事件原文。
8. **退款**：管理员批准退款的事务不变（按原逐件快照计算现金退款、返还与追回积分）；订单经 Stripe 付款且本次批准的现金退款额（不含运费）大于 0 时，同一事务另写一条 pending 的 `StripeRefund` 尝试，来源为该退款申请，金额为该现金退款额；现金退款额为 0（所退商品已被券与积分抵尽）时只处理积分与申请状态，不建尝试、不调用 Stripe。提交后调用 Stripe 退款接口：以该记录的本站 ID 为幂等键，并写进退款元数据；Stripe 退款 ID、调用结果与之后的退款事件（按 Stripe 退款 ID 或元数据里的记录 ID 关联）更新记录状态。Stripe 退款状态映射为本站状态：`pending` 与 `requires_action` 记为 pending，`succeeded` 记为 succeeded，`failed` 与 `canceled` 记为 failed。每条 `StripeRefund` 是一次尝试，有自己的本站 ID（即幂等键，并写进 Stripe 退款元数据）；同一来源至多一条不是 failed 的尝试，由数据库唯一约束保证。**只有 Stripe 明确给出 failed 或 canceled，或 Stripe 以请求错误明确拒绝创建（4xx，不含 409 与 429；这时没有建成退款）才记为 failed**；后一种不自动重试，记下错误类别并告警。其余一律保持 pending、占用额度。有 Stripe 退款对象的尝试，状态一律以向 Stripe 查询到的该退款当前对象为准（上面 4xx 明确拒绝创建的情形没有退款对象，是唯一例外；判断依据是 Stripe 返回的错误说明未建退款，不单凭状态码；409、429 与结果未知仍保持 pending）：退款事件只作触发，收到后先查询再更新，不按事件里的快照改，所以先后颠倒送达的事件不会让状态倒退；Stripe 允许已成功的退款之后变为失败，这时照查询结果改为 failed、释放额度。退款接口的响应、webhook 与定时查询共用同一写入规则：写入时锁住该尝试的行，只接受 pending → succeeded、pending → failed、succeeded → failed 三种改动，其余（如 succeeded → pending、failed → 任何状态）忽略，所以并发查询以相反顺序提交也不会倒退。已有 Stripe 退款 ID 而状态未终结的，等退款事件或由定时任务查询更新；已 succeeded 的尝试，定时任务在成功后 30 天内每天、之后每周再查询一次，不设终止（Stripe 没有给出成功退款不再变化的期限；演示站量小，查询成本可忽略），发现变为 failed 就照上面改并告警，防退款失败的 webhook 漏收。还没有 Stripe 退款 ID（调用结果未知或可重试的错误）的，由定时任务在该尝试创建后 24 小时内（Stripe 保留幂等键的最短期限）以同一幂等键自动重试，同一幂等键的并发请求不会在 Stripe 产生两笔退款；24 小时后不再调用退款接口，改为列出该 PaymentIntent 退款的全部分页、按元数据里的尝试 ID 对账，找到就采用；找不到或无法列完都保持 pending、占用额度，告警由运营者在 Stripe 后台跟进；本站不提供把这类尝试改为 failed 的手段，也就不会为同一来源另建尝试（测试环境不涉及真实资金，宁可少退也不重复退）。后台退款详情显示各次尝试的 Stripe 退款状态；最新一次尝试为 failed 时管理员可手动重试，重试是新建一条尝试（受上述唯一约束，重复点击与并发只有一个成功），再以它的 ID 调用 Stripe。**同一 PaymentIntent 的 pending 与 succeeded 退款合计不得超过付款金额**（failed 不计），新建前在锁住该付款的事务里核对，超出即不建并告警；这同时约束第 6 条的全额退款与本条的部分退款。按「计价、优惠、积分与库存」第 5 条，部分退款的累计本来就不超过商品现金实付合计（≤ 应付），这条是兜底。部分付款方式在 Stripe 有固定的退款期限：按 Stripe 文档，FPX 为付款后 60 天、GrabPay 为 90 天（实现前核验）；其他方式（卡、Link 等）本稿不定截止日。后台退款详情按记下的实际付款方式类型显示期限提示：FPX 为「Stripe 允许付款后 60 天内退款」，GrabPay 为「付款后 90 天内」，其他方式或类型为空时为「以 Stripe 为准」；只给提示、不计算具体日期（本站不保存 Stripe 认定的付款起算时间）；访客申请期限是付款后 30 天，管理员应在截止日前审核。逾期批准时 Stripe 若拒绝创建，按上文记为 failed 并告警，不阻止本站批准。本站的批准结果不因 Stripe 退款失败而回滚，访客看到的仍是模拟退款已批准。经模拟支付的订单退款不变。
9. **不可用**：创建会话或查询时 Stripe 不可用，支付页提示稍后再试，订单保持待支付直至按第 5 条取消，不自动改用模拟支付。CI 与本地测试用模拟的 Stripe 适配器，不调用 Stripe。
10. **资料与日志**：本站发给 Stripe 的只有金额、币种、行项目名称、内部订单 ID、语言、返回地址与预填的固定演示邮箱，不发送姓名、电话、地址或订单号。Stripe 付款页仍可能让访客修改邮箱，或按付款方式收集持卡人姓名与账单地址；这些由 Stripe 测试环境保存，本站不读取、不保存 Stripe 返回的客户资料、卡号片段或账单地址，也无法逐条删除。本站只存「数据模型」`StripeCheckout` / `StripeEvent` / `StripeRefund` 一行所列的对账字段（各类 Stripe ID、幂等键、金额、状态、实际付款方式类型、付款页地址、创建参数快照、事件类型、错误类别与时间），日志不记录 Stripe 请求与事件原文。跳转前的提示写明：只用测试卡号；Stripe 页上的邮箱、姓名与地址可填虚构资料，填入的内容由 Stripe 测试环境保存。实现前以实际的会话配置在测试页上核验哪些字段可编辑，与本条不符时先改设计。

## 权限与资料保护

- **结账身份**：未登录访客结账先填手机号。短信验证开关关闭时，任何号码都按下文的格式规则规范化后不发短信、以游客下单，该号码即订单收货电话与查单凭据；服务端创建订单时按开关的当前值判定，开关关闭即不因号码属于白名单而拒绝游客订单。以下白名单分支只在开关开启时适用。此时尚未选收货国家，页面提供国家码选择，默认 +60（马来西亚）；访客明确输入 `+` 国家码时以输入为准。服务端按所选国家码或输入的国家码规范化为 E.164，按下一条的格式规则检查，并以规范化结果判定是否属于白名单；之后选择的收货国家不改变已判定的号码。号码属于短信白名单国家时，先过人机挑战再发短信验证码；验证通过后，号码已注册且账号有效则登录该账号，未注册则创建无密码会员并登录，随后按下一条的规则自动认领该号码的游客订单，再以会员身份继续结账（可用券与积分、获得积分）。号码不属于白名单时不发短信，以游客下单，该号码即订单收货电话与查单凭据。开关开启时，服务端创建订单时强制执行：游客订单的收货电话属于白名单国家即拒绝，除非服务端记录显示该号码刚遇到短信无法送达或停发的降级情形，不依赖前端。已登录会员结账不再验证，收货电话默认为会员手机号，可改为其他号码或虚构号码。开关开启时，结账手机号旁告知：马新号码会收到验证短信并自动注册会员，手机号保留至注销，可随时在会员中心注销；开关关闭时改为告知短信验证已关闭、所有号码以游客结账；均无单独勾选框。
- 游客下单无需账号。游客订单的收货电话就是结账第一步按上一条规范化的号码，下单时不再按收货国家重新解析。会员改填的收货电话以收货国家作为默认区号解析自由文本；访客明确输入 `+` 国家码时以该号码为准。两种情形都只检查区号和长度等格式是否可能成立，不校验号码真实存在，以允许虚构演示资料；格式不成立则提示修改、不创建订单。注册、查单和订单认领都用相同的 E.164 规范化结果。查单先按高熵订单号定位，再与该单 `OrderRecipient` 的规范化号码比对；认领只查近 30 天且未认领的游客订单；开关开启时白名单号码通常不再出现在游客订单上，认领主要在短信降级下单或以后扩大白名单时生效；开关关闭期间马新号码也以游客下单，之后开启并由该号码持有人验证时，这些订单同样会被认领（Kelvin 2026-10-01 接受访客填写他人真实号码时，号码持有人借此看到所填收货资料的风险）。收货资料已存原文，原先的逐单 HMAC 盲索引不再提供额外保护，故删除该设计。查询成功后按 Kelvin 的决定可见完整姓名和地址，不再要求短信验证。查询接口严格限流、防批量枚举、不缓存敏感响应，订单号不出现在公共索引或分析事件。剩余风险仍是知道订单号和电话的人可读取完整地址。
- 注册、短信登录与结账验证是同一个短信验证流程：验证通过后号码已注册则登录，未注册则创建会员并登录。会员可用手机号加密码或手机号加短信验证码登录；未设密码的账号只能短信登录，密码登录对其与对错误密码返回相同的通用失败，不暴露账号是否存在或是否设了密码。首次设置密码在已登录会话内进行；已有密码的重设再次短信验证。短信登录与密码重设一样只证明对该号码的控制，信任基础与 1.6 相同。密码至少 8 位、不强制复杂度，安全哈希存储；会话到期、退出与服务端授权检查。账号注销须先以短信验证码确认（自动注册的账号可能从未设过密码），再撤销会话、删除手机号与密码，并把其订单上的会员 ID 清空以解除关联；游客订单被认领时写入不含手机号、不可撤销的「已认领」标记，会员下单的订单创建时即标记为不可认领，注销清空会员 ID 后这些标记保留，重新注册不能据此恢复旧订单的访问或积分；积分余额与未用券作废，积分和券使用流水保留去标识化审计记录。每个游客订单只能认领一次，注销后同号重注册不得再次认领或补发积分。**短信验证开关关闭期间**：注册、短信登录与密码重设暂停，前台明确提示；已设密码的会员仍可密码登录，未设密码的会员在开关重新开启前无法登录；已登录会员首次设置密码不受影响。注销确认改为：已设密码的会员输入当前密码；未设密码的会员在已登录会话内经二次确认即可注销（Kelvin 2026-10-01 决定，接受会话被盗用时账号可被他人注销的风险）；确认之后的注销步骤与开关开启时相同。注销时删除该会员的电话关联防套利索引，不保留跨账号用券计数；接受同号重注册可绕过每会员用券次数上限。注销不删除这些订单的收货资料，按「资料保留」长期保存。
- 管理员登录按来源与账号组合限流，连续失败后短时锁定并告警；锁定解除不绕过密码校验。单一管理员也须服务端授权与会话到期。
- 仅管理员可见所有订单原始资料、维护商品/运费/优惠、推进发货和审核退款。访客仅能访问已通过查询验证的订单：查单通过后，仅对该订单在本浏览器保持 30 分钟授权，只能查看该单、确认收货和申请退款，不能支付或取消，也不能替代其他订单的订单号加电话验证，过期须重新查单；每张游客订单（白名单外号码，以及白名单号码短信无法送达或停发时的降级下单）创建成功后，服务端只给当前浏览器发一个不可猜测、30 分钟有效且仅限该单的短期凭据，用于该单的模拟支付、失败重试、取消与结果页，这些页面可显示该单收货资料原文，凭据不能用于确认收货、退款或其他订单。短期凭据与查单授权都以服务端保存的会话实现，服务端校验所属订单、到期时间并可撤销；以 HttpOnly、Secure、SameSite=Lax 的 cookie 交给浏览器，不交给页面脚本，不写入浏览器持久存储、网址、Referer、日志、分析事件或错误回显；支付、取消、确认收货与退款申请等写操作另须 CSRF 令牌。一个浏览器可同时持有多张订单的授权，各自独立到期；会员仅能访问自己认领或下单的订单，并可在「我的订单」对这些订单确认收货、申请退款，规则与查单页相同。后台单一管理员也须认证，不把权限检查留给前端。
- 按 Kelvin 的新决定，收货资料不加密存储；访问受服务端权限控制并留审计记录，首版不提供后台导出，数据库账号与其他项目隔离。应用日志与监控不记录姓名、完整电话、地址、验证码、密码、订单查询参数。对外告知不会实际扣款或发货、资料用途及收货资料长期保存；无单独勾选框。
- **会员支付页与结果页的当前订单**（1.13）：会员的支付、取消、Stripe 发起与确认接口凭会员会话、以请求体里的订单号取单，前台没有订单号就无法继续；页面内存里的订单号在刷新或从 Stripe 返回（顶层整页加载）后会丢失。为此前台可把当前这一笔订单的订单号暂存在**本标签页的 sessionStorage**：只存这一个值，不存电话、收货资料、令牌或会话标识；不进地址、查询参数、localStorage、cookie、分析事件或日志。只有会员流程写入，游客流程不读也不写。写入：会员下单成功进入支付页时，以及从会员订单详情进入支付页时（覆盖之前暂存的值）。清除：该单支付结果确定（已支付、已取消，含超时取消与迟到付款按已取消处理）后，会员退出登录或注销时，以及会员接口对它回答会话无效或订单不存在时；关闭标签页时由浏览器清除。模拟支付失败、Stripe 确认中、会员接口暂时出错或网络中断都不算结果确定，不清除，重试时照用；结果确定后在结果页刷新，因暂存已清除而看到找不到订单的提示，这是可以接受的。服务端授权不变：每次仍凭会员会话校验该单属于本人，会话到期或已退出时会员接口不返回订单。**已知风险**：订单号是游客查单的两项凭据之一（另一项是电话），sessionStorage 与 HttpOnly cookie 不同，能被本站同源的脚本读取，共用电脑上未关闭的标签页也能读到；订单号本来就显示在支付页、结果页与我的订单里，增加的暴露面很小。

## 资料保留

- **收货资料长期保存**：按 Kelvin 2026-09-29 的决定，已支付与未支付订单的 `OrderRecipient` 原文都不再到期删除或匿名化，与订单商品、金额、状态、退款与积分流水一并保存；游客凭订单号与电话可随时查单，会员注销后收货资料也保留。取代 1.7 的「第 30 天删除」及对外「30 天后匿名化」的告知。游客订单自动完成规则见上方。
- 共享 `infra_mysql` 每天以 `mysqldump --all-databases` 备份整个实例，不能排除本项目的表。二进制日志配置的过期时间为 3 天，但 MySQL 只在日志轮换或重启时清理过期文件，当前活动文件不会被清理；共享实例的 `max-binlog-size` 为 256M，写入量小时轮换可能相隔数周。故 **binlog 残留期 = 当前 binlog 文件的轮换间隔 + 3 天**，轮换间隔待运营者核实。共享备份的实际保留天数记为 **N，待运营者核实**。收货资料不再删除，此残留期对它已无额外影响；会员注销时在线删除的手机号与密码哈希，最迟在注销后第 **max(binlog 残留期, N)** 天才从这些副本中消失；在两个期限未核实前，此式不构成确定的天数上限。不加密不保证物理介质取证级清除。
- **已知风险（Kelvin 已知悉并确认）**：马来西亚 PDPA 2010 的保留原则要求个人资料不得保存超过用途所需，演示站长期保存收货资料可能与之冲突，须由 Kelvin 自行取得法律意见；「知道订单号和电话的人可读取完整地址」这一剩余风险不再随时间消失，暴露面随订单累积。Kelvin 决定首版不提供访客删除收货资料的能力。在运营者核实 N、binlog 轮换间隔及共享备份确实会到期清理之前，不得宣称注销删除在备份中有确定上限。
- 会员手机号及密码哈希保留至主动注销，结账自动注册的会员同样适用，Kelvin 决定不对长期未登录的账号设到期注销；短信验证请求及发送记录短期保留用于防滥用；日志最长 30 天。注销删除失败或备份边界违规都向运营告警邮件报告，不能静默超期。会员支付页暂存在 sessionStorage 的订单号（「权限与资料保护」第 7 条）只在访客浏览器的当前标签页里，关闭标签页即清除，服务端不保存（1.13）。
- **Stripe 测试环境里的资料**：访客在 Stripe 测试付款页输入的持卡人姓名、账单地址等由 Stripe 测试环境保存，不在本项目数据库、binlog 或共享备份中，本项目无法逐条删除；运营者可删除整个测试环境。对外告知写明这一点，并提示只用测试卡号与虚构资料。
- 1.7 及以前「订单展示需求不构成永久保留个人资料的理由」的原则，对收货资料已被 Kelvin 上述决定取代，对其他个人资料仍然适用。若改变用途、字段、访问方式或保留期，本设计批准失效，须重审。
